- 起止：2026-07-20 立项 → 2026-07-21 合并 master
- 状态：**已完成并合并**（230 tests 全绿，typecheck clean），但**未达可上线**（见 §6）

## 1. 这个阶段做了什么

从一个空目录开始，交付了「腾讯会议导出网关」的服务端——一个企业内部署的组件，持有腾讯会议的 AK/SK 凭证，对客户端（CLI / 桌面端）提供**受策略管控的**会议资产清单与临时下载地址。

它解决的核心矛盾是：**既要让员工能导出会议资产，又要让企业管理员能管住谁导什么，还不能把删得掉全公司录制的高权限凭证发到每台终端上。** 答案是控制平面与数据平面分离——网关持凭证、做鉴权与策略，客户端凭网关签发的临时地址直连对象存储下载大文件。

## 4. 关键设计决策

| 决策 | 理由 |
| --- | --- |
| **网关模式**（而非 Token 分发器） | AK/SK 可删全公司录制，不能下发到客户端；策略只有在客户端够不到原始 API 时才管得住 |
| **控制/数据平面分离** | 大文件下载走客户端直连对象存储，网关只签发临时地址，不做字节搬运——网关因此可以是小机器 |
| **MySQL + 多实例可扩展** | 网关是服务端组件；所有跨请求状态入库，不放进程内存 |
| **assetId 自包含 meetingRecordId** | 让下载地址解析无状态，多实例安全，无需额外 API 往返 |
| **策略默认 deny** | 面对全公司会议录音，安全默认值优于可用默认值 |
| **JWT 不缓存策略结果** | 每次 download-url 实时评估策略，避免管理员收紧后出现 15 分钟管控空窗 |
| **设备授权流程（RFC 8628）** | CLI 无浏览器接不住 OAuth 回调，桌面端与 CLI 统一走设备流程 |
| **身份映射三策略可配置** | 企微 userid 与腾讯会议 userid 的对应关系未定，三种全实现，配置决定用哪种，不阻塞编码 |

## 5. 执行过程中审查拦下的缺陷

并行执行 + 独立审查的价值集中体现在这里。以下缺陷**在单元测试全绿的情况下依然存在**，靠审查者用真实依赖跑、带着不同问题查才暴露：

| 任务 | 缺陷 | 若漏到生产的后果 |
| --- | --- | --- |
| T4 | 身份邮箱查找无 `ORDER BY` | 邮箱复用（离职回收）时把甲的权限判给乙——越权 |
| T7 | Webhook 对畸形密文抛原生异常 | 公网端点泄漏栈信息 / OpenSSL 错误码 |
| T11 | 设备登录在真实 DB 下**完全不可用** | 26 测试全绿，却没有任何客户端能登录成功 |
| T12 | 资产缓存多实例下必失效 | 三类资产的下载地址解析在生产不可靠地失败 |
| T14 | 单会议详情漏整场可见性检查 | 无权用户按 ID 直接拿到会议主题、主持人 |
| 终审 | 腾讯错误分类在 HTTP 层被丢弃 | 配错凭证只返回不透明 500，运维排障无信号 |
| 终审 | 策略引擎 `end_time` 映射伪造数据 | 管理员以为按结束时间管控，实际按开始时间 |

七个缺陷里，T11 / T12 / 终审的错误分类三个尤其典型——它们不是「代码写错」，而是「测试替身比真实实现宽容」或「下游模块很努力、接缝却断开」，只有跨模块、用真实依赖才看得见。全部已修复并复审通过。

## 6. 未达可上线：遗留技术债

**代码完成 ≠ 可以上线。** 以下是最终整体审查判定的「上线前必须修」项，已建档但不阻塞合并这个动作。放生产流量前必须逐项清掉：

| # | 问题 | 风险 |
| --- | --- | --- |
| B1 | 登录端点零限流 × 服务账号时序预言机 | 可枚举 client_id + 无节流暴力 + 可当 DoS 接口 |
| B2 | JWT_SECRET 跨两个信任域复用，无强度校验 | 泄漏即可伪造任意用户令牌 + 解密全部 STS-Token |
| B3 | 策略引擎 NaN 比较静默放行 | 对非数值字段套 gte/lte 时规则被静默命中（过度放行） |
| B4 | 腾讯错误分类在 HTTP 层未映射 | 配错凭证 / operator 离职时只返回不透明 500 |
| B5 | STS 看门狗只接一半（expireStale 未调度） | STS 长期不可用时重复打腾讯 API + pending 行无界增长 |
| B6 | 企微扫码登录未接通 | verification_uri 指向不存在的 /device；仅凭网关走不完真人登录，US-2.1 待接通 |

**可带上线的技术债**（后续迭代）：meeting_cache 加 TTL、审计列复用清理、webhook 常量时间验签、若干测试夹具债。

完整清单见 `.superpowers/sdd/progress.md`（26 条，逐任务审查中判定「不阻塞」的项）。

## 7. 两个业务问题（✅ 已由项目方确认，2026-07-21）

这两个不是技术问题，由项目方从业务角度拍板。均已确认，且恰好与代码当前的安全默认值一致——无需改核心代码：

- **Q1：账号体系？** → 企业用**企微创建的账号，无独立体系、无 SSO**。故身份映射选定 **`direct`**。仍须 `preflight --sample-user` 实测确认企微 userid 与腾讯会议企业 userid 逐字节一致（腾讯同步实现细节），不一致则切 `table`（仅改配置）。
- **Q2：谁能导出？** → **仅管理员可导。** 当前最小安全模板（默认 deny + 一条「管理员 allow 全部」）即最终形态，此确认等于验收当前实现。

**连带影响**：Q2 的答案推翻了立项时「桌面版传播性好、员工都能用」的设想。既然只有管理员能导，**子项目 4（桌面应用）重新定位为管理员工具**（用户群几人到几十人），价值从「广泛传播」改为「让不熟命令行的管理员也能可视化操作」。用户故事与 spec 已据此更新。
