## 角色

| 角色 | 说明 |
| --- | --- |
| **企业管理员** | 腾讯会议超管 / 企业 IT，负责接入、配置策略、掌控数据边界 |
| **业务用户** | 普通员工，需要取回自己相关的会议资料 |
| **归档运维** | 负责建立长期自动归档机制的人（可能就是管理员） |

## 子项目标记

`P1` 导出网关 · `P2` 核心引擎/CLI · `P3` 存储扩展 · `P4` 桌面应用

## 1. 接入与部署

### US-1.1 确认企业具备接入条件 `P1`
**作为**企业管理员，**我想要**在投入实施前知道我的腾讯会议账号能否调用 API，**以便**不在不可能成立的方案上浪费时间。

验收标准：
- 文档明确列出账号版本要求（免费版/专业版不支持）
- 提供一条可执行的自检方式，能在部署前验证凭证与权限是否正确
- 版本不满足时给出明确结论，而非模糊的报错

### US-1.2 完成网关部署与凭证配置 `P1`
**作为**企业管理员，**我想要**按文档在阿里云部署网关并填入腾讯会议凭证，**以便**建立企业统一的导出通道。

验收标准：
- 凭证（SecretKey 等）不以明文形式存在于配置文件或数据库
- 配置错误时，启动阶段即报出具体原因（哪个凭证、哪项权限）
- 部署产物为容器镜像，不要求手工安装运行时依赖

### US-1.3 建立 STS-Token 自动续期 `P1`
**作为**企业管理员，**我想要**配置一次事件订阅后 Token 自动维持有效，**以便**不必人工干预凭证轮换。

验收标准：
- Token 在过期前自动续期，续期期间服务不中断
- 回调超时未收到 Token 时告警，且明确指出受影响的能力范围
- Webhook 端点拒绝未通过验签的请求

## 2. 数据管控

### US-2.1 限定可导出的数据范围 `P1`
**作为**企业管理员，**我想要**规定谁可以导出哪些会议的哪类资产，**以便**满足公司的数据管理要求。

验收标准：
- 规则可按人员、部门、会议属性、资产类型组合
- 未配置任何规则时默认拒绝
- 规则变更即时生效，无需重启

### US-2.2 管控无法被绕过 `P1`
**作为**企业管理员，**我想要**确信员工无法绕过策略直接取数，**以便**管控是真实有效的而非表面功夫。

验收标准：
- 客户端不持有腾讯会议凭证
- 构造他人的资产 ID 直接请求下载地址会被拒绝，而不仅是列表里看不到
- 拒绝行为留下审计记录

### US-2.3 签发与吊销自动化凭证 `P1`
**作为**企业管理员，**我想要**为定时归档任务签发独立凭证并能随时吊销，**以便**自动化任务与个人身份解耦。

验收标准：
- 服务账号凭证可设置有效期
- 吊销后即时失效
- 服务账号同样受策略约束

## 3. 导出会议资产

### US-3.1 按时间范围找到可导出的会议 `P2`
**作为**业务用户，**我想要**指定一段时间并看到我有权导出的会议，**以便**挑选需要归档的内容。

验收标准：
- 时间范围超过 31 天时由工具自动处理，用户无感
- 列表只包含策略允许的会议
- 会议显示主题、时间、主持人，足以辨认

### US-3.2 取回一场会议的全部资产 `P2`
**作为**业务用户，**我想要**把一场会议的录制、音频、逐字稿、AI 纪要一次性下载到本地，**以便**完整保存这场会议。

验收标准：
- 八类资产按可得性尽量取全
- 每类资产的缺失原因可查（未开放下载 / 尚未生成 / 策略拒绝）
- 文件按会议组织成目录，目录名可读

### US-3.3 中断后继续而非重来 `P2`
**作为**业务用户，**我想要**在网络中断或关机后重新运行时从断点继续，**以便**不必为一个几 GB 的录制重下一遍。

验收标准：
- 重新运行自动续传，无需专门的恢复命令
- 已完成的资产不重复下载
- 下载链接过期不导致从头开始

### US-3.4 知道当前进度与失败原因 `P2`
**作为**业务用户，**我想要**看到每个任务的状态和失败原因，**以便**判断是等待、重试还是放弃。

验收标准：
- 可查询各状态的数量与失败明细
- 失败原因是可理解的中文描述，而非原始错误码
- 可一键重试失败项

### US-3.5 等待延迟生成的 AI 纪要 `P2`
**作为**业务用户，**我想要**在录制已下载但纪要尚未生成时，工具能在纪要生成后自动补齐，**以便**我不必反复手工检查。

验收标准：
- 录制就绪即下载，不被未生成的纪要阻塞
- 后续运行时自动补齐已生成的纪要
- 确认不会生成的（未开放下载）立即标记，不无谓等待

## 4. 无人值守归档

### US-4.1 定时自动归档 `P2`
**作为**归档运维，**我想要**配置定时任务持续归档新产生的会议，**以便**建立长期的自动化归档机制。

验收标准：
- 命令可重复执行且幂等，重复运行不产生重复数据
- 使用服务账号凭证，无需人工扫码
- 单次运行失败不影响后续运行的正确性

### US-4.2 导出到企业存储 `P3`
**作为**归档运维，**我想要**把资产直接落到阿里云 OSS 或公司 NAS，**以便**归档数据进入企业既有的存储与备份体系。

验收标准：
- 存储目标可配置，切换目标不需要迁移已有记录
- 大文件写入支持中断续传
- 写入失败有明确错误，不产生残缺文件

## 5. 审计与合规

### US-5.1 核查数据导出记录 `P1`
**作为**合规审计，**我想要**查到谁在何时导出了哪场会议的哪类资产，**以便**在需要时说明数据流向。

验收标准：
- 每次签发下载地址均有记录
- 记录包含操作者、时间、会议、资产类型、策略判定结果
- 记录不可被普通用户修改或删除

### US-5.2 归档结果可脱离系统理解 `P2`
**作为**合规审计，**我想要**在存储上直接看懂归档目录的内容与完整性，**以便**不依赖导出工具本身也能核查。

验收标准：
- 每个会议目录包含元数据文件与资产清单
- 清单标明每项资产的原始 ID、大小、校验值
- 确认缺失的资产在清单中显式标注原因

## 6. 桌面端体验

### US-6.1 无需安装依赖即可使用 `P4`
**作为**业务用户，**我想要**下载安装包双击即用，**以便**不必安装运行时或命令行工具。

验收标准：
- macOS 与 Windows 各提供安装包
- 不要求用户安装 Bun、Node 或其他依赖
- 安装包经过签名，系统不拦截

### US-6.2 扫码登录 `P4`
**作为**业务用户，**我想要**用企业微信扫码登录，**以便**不必记额外的账号密码。

验收标准：
- 扫码后进入应用，身份与企微账号一致
- 登录状态可保持，过期后重新扫码
- 可主动退出登录

### US-6.3 可视化查看与操作任务 `P4`
**作为**业务用户，**我想要**在界面上看到会议列表和下载进度并控制任务，**以便**不必使用命令行。

验收标准：
- 显示每个任务的进度与状态
- 可暂停、继续、重试
- 桌面端与 CLI 使用同一份数据，交替使用不冲突

## 7. 需求验证问题

以下是我从设计文档反推用户故事时发现的问题。**它们在设计文档中没有答案**，需要你判断。

### Q1. 企微身份与腾讯会议身份如何对应？（阻断性）

策略引擎要判断「这场会议你能不能导」，判断依据是会议的主持人、所属部门等**腾讯会议侧**的属性（`host_user_id` 是腾讯会议的 `userid`）。

但客户端登录用的是**企业微信身份**。两套 ID 体系：

```
企微 userid  ──?──►  腾讯会议 userid
```

- 若企业通过企微对接腾讯会议 SSO，两者可能天然一致
- 若不一致，网关必须维护一张映射表，且人员变动时需同步

**这直接决定 US-2.1 能否实现**。设计文档假设了策略可以按人判断，但没说这个映射从哪来。需要确认贵司的实际情况。

### Q2. 默认的组织策略是什么？

设计文档定义了策略**机制**（规则模型、默认 deny），但没定义**默认应该配什么规则**。这是需求问题不是技术问题：

- 员工能导出自己**主持**的会议吗？
- 能导出自己**参与但非主持**的会议吗？
- 部门负责人能导出本部门所有会议吗？
- 还是一律只有管理员能导，员工需申请？

不同答案会导出完全不同的产品形态。US-3.1 和 US-3.2 目前是按「员工能自助导出」写的，如果实际是「只有管理员能导」，那 US-6.1/6.2 的桌面端传播性诉求就不成立。

### Q3. 导出之后的文件谁能访问？

设计文档管住了「谁能**导出**」，但没管「导出后谁能**看**」。资产落到 NAS 或 OSS 后，访问控制由文件系统或对象存储的权限体系决定，与我们的策略引擎完全无关。

结果可能是：策略严格限制了 A 不能导出 B 部门的会议，但 A 能直接打开 NAS 上别人导出的同一批文件。**管控在这一步失效。**

需要确认：导出目标的权限体系由谁管？是否需要按会议/部门写入不同的目录并施加不同权限？

### Q4. 子项目 1 单独交付时没有可演示的用户价值

网关交付后，管理员完成了部署和配置——然后什么也做不了，因为没有客户端。上面所有 `P2`/`P4` 的故事都还不可用。

这不是设计问题，是**交付节奏问题**。需要确认验收方式：

- 是接受「子项目 1 以 API 契约 + 自动化测试验收」，还是
- 需要一个最小的验证客户端（哪怕是 curl 脚本集）来演示端到端跑通

我建议后者，成本很小但能真正验证网关可用。

### Q5. 48 小时等待期在产品上如何表达？

AI 纪要可能需要等待数十小时。这段时间里一场会议处于「录制已下载、纪要待生成」的部分完成状态。

US-3.5 假设用户能接受这种异步，但界面上如何表达？

- 显示为「已完成（部分）」还是「进行中」？
- 用户会不会误以为工具卡住了？
- 是否需要在导出完成时明确告知「纪要将在生成后自动补齐」？

### Q6. 会议范围的默认口径未定

`GET /v1/records` 需要传时间范围，但**默认查谁的会议**没有定义。网关用固定 operator 账号调用，该账号是企业管理员——理论上能看到全企业的录制。

那么：
- 客户端不传任何过滤条件时，返回全企业会议还是仅与该用户相关的会议？
- 「相关」的定义是什么（主持 / 参与 / 本部门）？

这与 Q2 相关，但更具体地影响 US-3.1 的实现和默认体验。
