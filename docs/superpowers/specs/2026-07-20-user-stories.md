## 1. 接入与部署

### US-1.1 确认企业具备接入条件 `P1`
**作为**企业管理员，**我想要**在投入实施前知道我的腾讯会议账号能否调用 API，**以便**不在不可能成立的方案上浪费时间。

- 明确列出账号版本要求：免费版与专业版**不支持调用任何 REST API**
- 提供可执行的自检方式，部署前即可验证凭证与权限
- 版本不满足时给出明确结论，而非模糊报错

> 依据 spec §3.4。这是阻断性前提，须最先确认。

### US-1.2 完成网关部署与凭证配置 `P1`
**作为**企业管理员，**我想要**按文档在阿里云部署网关并填入腾讯会议凭证，**以便**建立企业统一的导出通道。

- SecretKey 等凭证不以明文存在于配置文件或数据库
- 配置错误时启动阶段即报出具体原因（哪个凭证、哪项权限）
- 部署产物为容器镜像，不要求手工安装运行时依赖

### US-1.3 建立 STS-Token 自动续期 `P1`
**作为**企业管理员，**我想要**配置一次事件订阅后 Token 自动维持有效，**以便**不必人工干预凭证轮换。

- Token 在过期前自动续期，续期期间服务不中断
- 回调超时未收到 Token 时告警，并明确指出受影响的能力范围（AI 纪要不可用，录制与逐字稿不受影响）
- Webhook 端点拒绝未通过验签的请求

> 依据 spec §5.3。回调为异步下发，因此按剩余有效期 1/3 提前触发，新旧 Token 并存。

### US-1.4 确认身份映射可用 `P1`
**作为**企业管理员，**我想要**在上线前验证管理员的企微身份能正确对应到腾讯会议账号，**以便**策略能真正按人生效。

- 支持 `direct` / `email` / `table` 三种映射策略，可配置；**本项目选用 `direct`**（见 Q1）
- 提供工具用真实账号实测映射结果（`preflight --sample-user`）
- 映射不通时给出的是配置错误提示，而非把用户当作「无权限」

> 依据 spec §5.4.4。**这是阻断性前提**：账号来自企微、无 SSO，`direct` 为首选；须 preflight 实测确认企微 userid 与腾讯会议企业 userid 一致，不一致则切 `table`。若无法可靠对应，US-2.1 不成立。

## 2. 数据管控

### US-2.1 限定可导出的数据范围 `P1`
**作为**企业管理员，**我想要**规定谁可以导出哪些会议的哪类资产，**以便**满足公司的数据管理要求。

- 规则可按人员、部门、会议属性、资产类型组合
- 未配置任何规则时默认拒绝
- 规则变更即时生效，无需重启
- 规则可被管理员读懂并审计（仅等值、集合包含、时间区间三种操作，无嵌套逻辑）

> 依据 spec §5.5。默认 deny 意味着**装好后不配规则是不能用的**，见 Q2。

### US-2.2 管控无法被绕过 `P1`
**作为**企业管理员，**我想要**确信员工无法绕过策略直接取数，**以便**管控是真实有效的而非表面功夫。

- 客户端不持有腾讯会议凭证
- 构造他人的资产 ID 直接请求下载地址会被拒绝，而不仅是列表里看不到
- 收紧策略后，持有未过期令牌的用户下一次请求即被拒（令牌内不缓存策略结果）
- 拒绝行为留下审计记录

> 依据 spec §4.1 与 §5.5。三个执行点中，只有「换下载地址」是真正的授权检查。

### US-2.3 签发与吊销自动化凭证 `P1`
**作为**企业管理员，**我想要**为定时归档任务签发独立凭证并能随时吊销，**以便**自动化任务与个人身份解耦。

- 服务账号凭证可设置绝对过期时间
- 吊销后即时失效
- 服务账号同样受策略约束，不享有绕过特权
- 密钥明文仅在签发时展示一次

### US-2.4 看清每场会议卡在哪一段 `P5`
**作为**数据管理员，**我想要**看到每场会议现在处在「拉取 → 归档 → 本地保留 → 采集授权」四段中的哪一段、这一段是成功还是失败，**以便**在数据永久丢失之前先发现归档失败的会议。

- 归档只有在本地文件成功写入 NAS **且哈希校验通过**之后才记为成功；校验不符就不落归档记录、也不删本地文件
- 一场会议的所有已完成资产都归档成功，这场会议才算归档完成
- 归档失败在会议记录页的分诊条里单独成格（红色）——它到期就会永久丢失，是全系统唯一不可逆的损失

> 依据控制台说明书 §4.2 分诊条、§4.3 详情抽屉四段。

### US-2.5 撤销归档 `P5`
**作为**数据管理员，**我想要**把一场会议的归档结果撤销掉重来，**以便**归档到了错误位置、或需要重新组织 NAS 目录时，不必手工改数据库。

- 撤销后该会议回到「未归档」，归档流水线可以重新拾起它
- **待定**：撤销是否连带删除 NAS 上已写入的副本，说明书没写明——实现前必须先定，因为这决定了它是不是一个不可逆动作

> 依据控制台说明书 §4.3 第 2 段「撤销归档」。**当前无任何实现**，见 §9.5。

### US-2.6 延长本地保留 `P5`
**作为**数据管理员，**我想要**给快到期的会议延长本地保留期，**以便**还在用的会议不会因为窗口到点被清理走。

- 延长是在**现有到期时间上加天数**，不是从今天重新起算
- 会议记录页每行 hover 出「+30 天」，详情抽屉里是同一个动作
- 勾选多场会议后可一次性批量延长

> 依据控制台说明书 §4.2 表格列「本地保留」、§4.3 第 3 段。

## 3. 登录与身份

### US-3.1 扫码登录 `P1` `P4`
**作为**业务用户，**我想要**用企业微信扫码登录，**以便**不必记额外的账号密码。

- 扫码后进入应用，身份与企微账号一致
- 身份无法映射到腾讯会议账号时，提示「账号未开通」而非「无权限」
- 授权页面被他人诱导扫码时无法劫持会话（`state` 一次性校验）

### US-3.2 CLI 用服务账号认证 `P2`
**作为**归档运维/管理员，**我想要**在服务器或终端上用服务账号凭证让 CLI 认证到网关，**以便**在无浏览器环境下也能跑导出，且不必在每台机器上交互登录。

- CLI 从环境变量读服务账号 `client_id` / `client_secret` 与网关地址，**非交互认证**
- 访问令牌仅在进程内存持有，**本地不落任何凭证**；令牌过期自动重换，长任务不中断
- 凭证配置错误时给出明确原因，而非笼统失败

> **M3 决策（2026-07-23 spec §7）**：M3 的 CLI 认证定为**服务账号、无状态**，与 Q2「仅管理员可导」自洽——导出者是管理员，用服务账号身份即可，无需业务用户各自在 CLI 里扫码登录。这条也让 US-5.1（定时归档用服务账号）成为 CLI 的常态而非特例。
>
> **原「命令行扫码登录（设备授权流程 RFC 8628）」已从 M3 移出**：网关侧的设备流程已实现（子项目 1 的 `/device`），**保留为未来能力**——将来若放开员工自助导出、或桌面端（P4）需要交互式登录，可直接复用；M3 的 CLI 不构建交互式登录。

### US-3.3 保持登录与主动登出 `P1` `P4`
**作为**业务用户（交互式登录场景），**我想要**登录状态能保持一段时间，也能在需要时主动退出，**以便**日常使用不必反复扫码，换机器时又能确保凭证失效。

- 登录状态保持 7 天，期间自动续期无感
- 主动登出后旧凭证立即失效
- 凭证被窃取并重放时，系统能察觉并吊销该用户全部会话

> 依据 spec §5.4.5。刷新即轮换 + 重放检测。
> **不适用于 M3 的 CLI**（已去 `P2` 标记）：M3 的 CLI 用**服务账号无状态**认证，无 refresh_token、不持久化登录（见 US-3.2），因此「7 天保持 + 轮换 + 登出」这套只对交互式登录（网关能力 P1、桌面端 P4）成立。

### US-3.4 用独立账号登录控制台 `P5`
**作为**数据管理员，**我想要**用一套独立于企微的账号密码登录控制台，**以便**在企微或腾讯会议本身不可达时，我仍然进得来处理故障。

- 账号 + 密码 + 「记住此设备 30 天」；无自助注册、无找回密码
- 登录失败只给**表单级**统一文案「账号或密码错误」，不指出是哪个字段错；账号存在与否也不能产生可观测差异（含耗时）
- 勾选「记住此设备」得到长会话，不勾选得到短会话——**两者的实际时长必须真的不同**
- 主动登出后该会话立即失效

> 依据 D1（2026-08-23，见 roadmap M6）与控制台说明书 §4.1。
> **为什么不复用企微扫码登录**：控制台的价值恰恰在 NAS 断连、企微不可达这类故障时刻，登录不能依赖另一个可能同时挂掉的系统。这是与 US-3.1 并列的第三条认证线，不是它的替代。

### US-3.5 管理运维账号 `P5`
**作为**数据管理员，**我想要**自己添加与移除其他运维人员的账号，**以便**1–3 人的运维团队能自己管进出，不必每次找人改数据库。

- 移除账号后，该账号的**全部在途会话立即失效**，不等自然过期
- 系统内至少保留一个账号；删到只剩一个时拒绝，避免把自己锁在外面
- 首个账号由 CLI bootstrap 脚本创建，且该脚本**只在账号表为空时可用、建完自动失效**

> 依据控制台说明书 §2 角色与权限、§4.1「忘记密码请联系系统管理员开通」。

## 4. 查找与导出

> **当前策略下（Q2 已确认：仅管理员可导），本 Epic 的实际使用者是管理员。**
> 普通员工登录后策略判定为 deny，看不到也导不出任何会议。保留「业务用户」措辞是为将来放开员工自助导出时无需重写。

### US-4.1 浏览一段时间内的会议 `P1` `P2`
**作为**业务用户（当前即管理员），**我想要**指定一段时间并看到我有权导出的会议，**以便**挑选需要归档的内容。

- 时间范围超过 31 天时由工具自动切分，用户无感
- 列表只包含策略允许的会议
- 显示主题、时间、主持人，足以辨认

### US-4.2 导出指定的某一场会议 `P1` `P2`
**作为**业务用户，**我想要**凭手上的会议号找到并导出那一场会议，**以便**不必为了一场会而导出整个月。

- 支持用会议号（9 位，邀请函上的号码）查找，不要求用户知道内部会议 ID
- 一个会议号命中多场会议时，列出全部候选供选择，不擅自择一
- 会议不在默认时间范围（最近 31 天）内时，提示「可扩大时间范围」，而非笼统的「未找到」
- 与批量归档混用时不产生重复下载

> 依据 spec §5.2 与 A.8。平台侧 `start_time`/`end_time` 为必填，
> 不存在「仅凭会议 ID 查询」的路径，故有默认窗口这一设计。

### US-4.3 取回一场会议的资产 `P2`
**作为**管理员，**我想要**把一场会议的资产下载到本地，**以便**完整保存这场会议。

- **默认取四类**：录制视频、录制音频、逐字稿（原始转写）、逐字稿（智能优化版）——即资产 ①②③④
- **AI 会议纪要（章节 / 主题 / 发言人 / DeepSeek）默认不取**，`--assets` 可显式加（工具字段驱动，`--assets all` 取全八类）
- 每类资产的缺失原因可查（未开放下载 / 尚未生成 / 策略拒绝 / 超时放弃）
- 文件按会议组织成目录，目录名可读；扩展名与实际格式一致（txt / pdf / docx / htm）

> **M3 决策（2026-07-23 spec §5）**：默认资产集收敛为 ①②③④。**「时间轴」不单列一类**——时间轴信息内嵌在 AI 纪要里（章节纪要按时间分段、发言人纪要为带时间的发言序列），随对应纪要一并得到。会议纪要能力保留为 opt-in（`--assets`）。默认集里 ①②③ 免 STS、走 6h 快档，仅 ④ 需 STS、走 48h 探测。

### US-4.4 只导出需要的资产类型 `P2`
**作为**管理员，**我想要**指定只下载某几类资产（如只要逐字稿而不要几 GB 的视频），**以便**快速拿到真正需要的内容。

- 用 `--assets` 按类型筛选，键为 `video` / `audio` / `transcript` / `ai_transcript`（默认四类）+ `ai_minutes` / `ai_topic_minutes` / `ai_speaker_minutes` / `ai_ds_minutes`，亦接受 `all`
- 未知键报错并列出合法键，不静默忽略
- 未选中的类型不产生下载任务，也不占用配额
- 事后可补充导出其余类型，已导出的不重复（资产粒度去重）

### US-4.5 中断后继续而非重来 `P2`
**作为**业务用户，**我想要**在网络中断或关机后重新运行时从断点继续，**以便**不必为一个几 GB 的录制重下一遍。

- 重新运行自动续传，无需专门的恢复命令
- 已完成的资产不重复下载
- 下载链接过期不导致从头开始（链接仅 5 分钟有效，大文件必然中途过期）

### US-4.6 知道当前进度与失败原因 `P2`
**作为**业务用户，**我想要**看到每个任务的状态和失败原因，**以便**判断是等待、重试还是放弃。

- 可查询各状态的数量与失败明细
- 失败原因是可理解的描述，而非原始错误码
- 可一键重试失败项

### US-4.7 等待延迟生成的 AI 纪要 `P2`
**作为**业务用户，**我想要**在录制已下载但纪要尚未生成时，工具能在纪要生成后自动补齐，**以便**不必反复手工检查。

- 录制就绪即下载，不被未生成的纪要阻塞
- 后续运行时自动补齐已生成的纪要
- 确认不会生成的（未开放下载）立即标记，不无谓等待

> 依据 spec A.4。`allow_download=false` 时可即时判定，
> 超时上限（视频 6 小时 / 纪要类 48 小时）仅作安全网。产品表达见 Q5。

## 5. 无人值守归档

### US-5.1 定时自动归档 `P2`
**作为**归档运维，**我想要**配置定时任务持续归档新产生的会议，**以便**建立长期的自动化归档机制。

- 命令可重复执行且幂等，重复运行不产生重复数据
- 使用服务账号凭证，无需人工扫码
- 单次运行失败不影响后续运行的正确性
- 非交互环境下遇到歧义（如会议号多结果）直接失败并给出候选，不自动择一

### US-5.2 导出到企业存储 `P3`
**作为**归档运维，**我想要**把资产直接落到阿里云 OSS 或公司 NAS，**以便**归档数据进入企业既有的存储与备份体系。

- 存储目标可配置，切换目标不需要迁移已有记录
- 大文件写入支持中断续传
- 写入失败有明确错误，不产生残缺文件

> **2026-08-25 收敛**：OSS 至今无需求方，本条实际只交付了 NAS 一侧。见 §9.4。

### US-5.4 查看 NAS 挂载与容量状态 `P5`
**作为**归档运维，**我想要**看到 NAS 的连通状态、最近检测时间与容量占用，**以便**在归档开始批量失败之前就知道 NAS 出了问题。

- 显示挂载点、协议、连通状态、最近检测时间
- 容量分「本系统占用 / 其他占用 / 剩余」三块
- **NAS 不可达时，探测必须在有限时间内返回明确的降级结果，而不是挂起**——探测本身不能变成新的故障点

> 依据控制台说明书 §4.9「NAS 归档」块、§7.2 NAS 断连。

### US-5.5 配置默认保留天数 `P5`
**作为**归档运维，**我想要**配置新归档会议的默认本地保留天数，**以便**按公司口径统一保留窗口，而不是一场一场手工设。

- 设置持久化，重启后仍生效
- 只影响此后**新归档**的会议，不回溯改已有会议的到期时间

> 依据控制台说明书 §4.9「本地保留窗口」的三个动作之一。

### US-5.6 立即清理已到期文件（含预览）`P5`
**作为**归档运维，**我想要**先看清楚这次到底会删哪些会议的哪些文件，再决定是否真删，**以便**这个不可逆动作不会因为一次误点就丢数据。

- **默认是预览（dry-run），不删任何东西**；真删必须显式二次确认
- 删之前**重新校验 NAS 副本的哈希**；读不到或对不上就整场拒删，留在原地等人工介入
- 有一个持久化的暂停开关；打开后不再删任何东西，**且重启后仍然是暂停状态**
- 到期只删本地文件，**数据库记录永久保留**（标题、时间、主持人、内容哈希、NAS 目录），历史会议依然搜得到，只是要按给出的路径去 NAS 取

> 依据控制台说明书 §4.9 及该页底部那段必须保留的说明。**这是全系统唯一不可逆的动作**，M6 阶段 2 把它判为最高风险故事。

## 8. 需求验证问题

**Q1、Q2 已由项目方确认（2026-07-21），结论并入下方。Q3–Q6 仍待判断。**

### Q1. 企微身份与腾讯会议身份如何对应？（✅ 已确认）

**项目方确认的事实**：企业没有独立的账号体系，未使用 SSO，用户直接使用企业微信创建的账号。

**结论**：无 SSO 转换层，登录身份即企微身份，采用 **`direct`** 策略（`IDENTITY_STRATEGY=direct`）。

| 策略 | 前提 | 本项目 |
| --- | --- | --- |
| `direct` | 企微 userid 与腾讯会议企业 userid 同源 | **✅ 选用** |
| `email` | 两侧均有可靠且唯一的邮箱 | 备选 |
| `table` | 管理员维护显式映射表 | fallback |

**仍需一次 preflight 实测（不是不信任答案，是腾讯生态的实现细节）**：企业通过企微开通腾讯会议时，腾讯会议企业 userid 是否与企微 userid **逐字节一致**，取决于腾讯侧的同步实现。用 `scripts/preflight.ts --sample-user <真实企微userid>` 验证 `direct` 能否解析出正确的腾讯会议 userid。

- 若一致 → `direct` 直接可用。
- 若不一致（腾讯会议侧对 userid 做了转换或加了前缀）→ 切 `table`，用企微通讯录同步一张映射表。这不影响代码，只改配置与一次性数据导入。

对应 US-1.4、spec §5.4.4 与 §6。

### Q2. 默认的组织策略是什么？（✅ 已确认）

**项目方确认**：**只有管理员能导出。**

**结论**：当前的最小安全模板即为最终形态——`policy_rules` 无种子数据（默认 deny），只配一条「管理员 allow 全部」。代码无需改动，此确认即验收当前实现。

**连带影响（重要，推翻了立项时的设想）**：

- 立项 brainstorming 时的设想是「桌面版传播性好、员工都能导自己的会议」。**该设想不成立**——既然只有管理员能导，桌面端的用户群是**管理员**（通常几人到几十人），不是全员。
- 因此**桌面端（子项目 4）重新定位为「管理员工具」**，而非全员传播型产品。US-7.1 的「传播性」诉求作废，其价值改为「让不熟命令行的管理员也能操作」。
- Epic 4（查找与导出）诸故事的实际可用角色是**管理员**，而非「业务用户」。见下方 §8.1 的角色修正说明。

> 机制与策略的区分仍然成立：策略引擎在能力上支持任意粒度授权（给某人 allow 某些会议）。「只有管理员能导」是一条**策略配置**，不是代码限制。将来若组织决定放开员工自助导出，改策略规则即可，无需改代码。

### 8.1 因 Q2 确认而做的角色修正

Epic 3（登录与身份）、Epic 4（查找与导出）中标注角色为「业务用户」的故事，在当前策略下**实际使用者是管理员**（普通员工登录后策略判定为 deny，看不到也导不出任何会议）。这些故事的能力描述与验收标准依然有效，只是主体收敛为管理员。保留「业务用户」措辞是为了：一旦将来放开员工自助导出，这些故事无需重写即可生效。

### Q3. 导出之后的文件谁能访问？

spec 管住了「谁能**导出**」，没管「导出后谁能**看**」。资产落到 NAS 或 OSS 后，访问控制由文件系统或对象存储决定，与策略引擎无关。

可能的结果：策略禁止 A 导出 B 部门的会议，但 A 能直接打开 NAS 上别人导出的同一批文件——**管控在最后一步失效**。

需确认：导出目标的权限体系由谁管？是否需要按部门写入不同目录并施加不同权限？

### Q4. 子项目 1 单独交付时没有可演示的用户价值（✅ 由 M3 回答）

> **2026-07-23 更新**：M3（本次）正是那个缺失的客户端。`mde` CLI 一旦交付，`P2` 故事即端到端可用（列会议、导出、断点续传、延迟补齐），网关的用户价值随之落地。Q4 关心的「需要一个客户端演示端到端」正通过 M3 落实——不再是待决问题，而是正在进行的工作。

（历史记录）网关交付后，管理员完成部署和配置——然后什么也做不了，因为没有客户端。上面所有 `P2`/`P4` 故事都还不可用。当时建议做一个最小验证客户端演示端到端；M3 是这个客户端的完整版。

### Q5. 48 小时等待期在产品上如何表达？（CLI 侧由 M3 回答；桌面侧 P4 仍开放）

> **2026-07-23 更新（CLI 侧）**：M3 spec §9/§12 的机制回答了「工具会不会像卡住」——CLI **跑完即退出、不在后台空等**，把等待状态落进 SQLite：未就绪资产记为 `probing`、确认不可得记为 `skipped(download_not_allowed)`、超 deadline 记为 `skipped(upstream_timeout)`；`mde status` 显示各状态计数与原因，cron 反复跑自动补齐。用户看到的是「录制已完成 + 纪要 probing/skipped」的明确分项状态，而非一个卡住的进度条。
> 又：默认资产集只有 ④ 属 48h AI 类（①②③走 6h 快档），这个「长等待」在默认路径里是窄场景。
>
> **桌面侧（P4）仍待定**：GUI 上「部分完成」如何可视化呈现（进度条 / 分项徽标 / 主动提示「纪要将自动补齐」）是 P4 的 UX 问题，M3 不涉及。

（原始问题）AI 纪要可能需等待数十小时，期间会议处于「录制已下载、纪要待生成」的部分完成状态。显示为「已完成（部分）」还是「进行中」？用户会不会误以为工具卡住？是否需要在导出结束时明确告知「纪要将在生成后自动补齐」？

### Q6. 会议范围的默认口径未定

网关用固定 operator 账号（企业管理员）调用，理论上能看到全企业录制。那么客户端不传过滤条件时：

- 返回全企业会议，还是仅与该用户相关的会议？
- 「相关」的定义是什么（主持 / 参与 / 本部门）？

与 Q2 相关，但更具体地影响 US-4.1 的默认体验。

**一句话小结**：31 条故事里 `✅` 17 条、`◐` 10 条、`⬜` 2 条、`⏸` 2 条。其中 3 条标了「✅（P1 侧）」——US-3.1 / US-3.3 / US-4.1 的网关能力是完整的，但它们同时挂着的 `P2` / `P4` / `P5` 那一侧另有说法，看该行的缺口列。

**`◐` 集中在同一个原因上**：M6 阶段 2 交出的是**能力**，不是**入口**。归档、保留、清理、探测、账号管理的逻辑都跑得起来、也有测试，但除了登录之外没有一条控制台 API（阶段 4 的 A2–A6），也没有除登录页与会议记录页骨架之外的界面（阶段 5 的 F2–F7）。**在 A2–A6 与 F2–F7 落地之前，这 10 条对使用者来说等于不存在。**

**两条 `⬜` 的性质不同**：US-6.2 是被明确记账的遗留债（roadmap M3 「可带上线的债」第一条）；US-2.5 是**计划声称覆盖、交付里没有**，见下。
