**根因**（值得记住，避免再犯）：客户端的 `RawAsset` 是 T6 时**推断**网关契约写的；
e2e 假网关又是照着客户端的 `RawAsset` 写的。于是「推断 → 按推断造替身 → 替身验证通过」
形成闭环自证，而真网关从头到尾没参与过。**凡「我方 A ↔ 我方 B」的契约，直接比对双方源码，
不要用替身验证**；真实环境只用来验证我们控制不了的那一侧（腾讯 / 企微 / 对象存储）。

> 这两条是**读代码**发现的，不是联调发现的——因为两端都是我们自己的代码。
> 教训：凡是「我方 A 组件 ↔ 我方 B 组件」的契约，都应当直接比对两边源码，而不是等真实环境。

## Stage 2 · 网关单机自检（preflight）

**这是全流程性价比最高的一步**：一条命令覆盖 7 项检查，含 M3.5 的两个既定目标（身份映射实测、STS webhook 实测）。

```bash
bun scripts/preflight.ts --sample-user <真实企微userid>
# IDENTITY_STRATEGY=email 时，additionally: --sample-email <该用户邮箱>
```

preflight 的 7 项：

| # | 检查 | 失败意味着 |
| --- | --- | --- |
| 1 | 配置完整性 | `.env` 缺项或格式错；后续项会被跳过 |
| 2 / 2b / 2c | 数据库连通 / 字符集 utf8mb4 / 版本 ≥5.7 | 见 deploy.md §2，字符集必须建库时指定 |
| 3 | 腾讯凭证与签名（真调 `/v1/records`） | 凭证错 / 签名实现与平台不符 / 网络不通 |
| 4 | 账号版本 | 由第 3 项推出——免费版/专业版会在第 3 项失败 |
| 5 | 企微凭证（真调 `gettoken`） | CorpId/Secret 错 |
| 6 | **身份映射策略实测** | **M2 的 Q1 在此定论**：`direct` 不通就切 `table`（仅改配置，见 deploy.md §6） |
| 7 | **STS-Token 可达性** | 发起真实申请并等 Webhook 回调配对。不通 = 公网地址/验签/加解密有问题 |

**通过判据**：7 项全 PASS。

**第 6 项的处置**：这是 M2 遗留问题的答案。
- PASS → 确认 `IDENTITY_STRATEGY=direct`，Q1 闭合
- FAIL → 改用 `table` 策略并维护对照表（deploy.md §6），**不需要改代码**

**第 7 项的处置**：这是 deploy.md §11 的 webhook 格式核实。
- FAIL 时先看是超时还是验签/解密失败。webhook 线路格式（query 带签名 + body `{encrypt}`）系**仿企微自行设计、未对照腾讯官方文档核实**，这里就是核实它的地方。若格式不符，改 `src/sts/crypto.ts` 的解析，注意 `.superpowers` 台账记过「该算法在四处独立维护，改动需同步」。

- [ ] 第 7 项结论记录：webhook 格式是否与设计一致 ________

## Stage 3 · 起服务 + 种子数据

### 3.1 起网关

```bash
bun src/index.ts    # 或按 deploy.md §8 的容器方式
curl -s localhost:<port>/healthz
```

### 3.2 播策略种子（**最容易踩的坑**）

采集权限规则栈（`kind='allow'`）**兜底 deny**。`policy_rules` 空表 = 谁都导不了，
而表现是**资产列表返回空数组**——与「这场会议真的没有资产」看起来一模一样。

按 deploy.md §7 的最小安全模板插入一条 allow 规则。**规则的 `subject_value` 填
服务账号的 id（= `MDE_CLIENT_ID`），不是腾讯会议 userid**——采集权限的主体是
采集程序，不是人。本地/联调直接跑 `bun scripts/seed-dev.ts` 更省事，它把规则主体
与账号 id 由同一个变量产生，从结构上消除填错的可能。

### 3.3 建服务账号（拿客户端凭证）

客户端用服务账号认证。`service_accounts` 表字段：`id`(=client_id) / `name` /
`secret_hash`(argon2id) / `tm_userid` / `enabled` / `expires_at` / `created_at`。

生成 hash（**不要把明文 secret 写进任何提交的文件**）：

```bash
bun -e 'console.log(await Bun.password.hash(process.env.S, {algorithm:"argon2id"}))'
# 用法：S='你自己生成的强随机密钥' bun -e '...'
```

然后 INSERT 一行。`id` 必须与上一步规则的 `subject_value` **是同一个值**，
否则规则不对这个程序生效，现象同样是「空列表」。`tm_userid` 只用于审计留痕与
调用腾讯会议 API，**不参与策略判定**，填错不会导致拒绝，但会让审计记错人。

## Stage 7 · 下载地址 + 真实下载

```bash
AID=<上一步某个 asset_id>
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  "$MDE_GATEWAY_URL/api/v1/assets/$AID/download-url" | jq .
```

**通过判据**：返回 `{"url":"...","expires_at":<秒>,...}`。

然后**验证对象存储是否支持 Range**——断点续传全靠它：

```bash
URL='<上一步的 url>'
curl -s -o /dev/null -D - -H 'Range: bytes=0-1023' "$URL" | head -5
```

**通过判据**：`HTTP/1.1 206 Partial Content` 且有 `Content-Range` 头。

- 若返回 **200 而非 206** → 对象存储忽略 Range。客户端会 `discardPart` 重下（有此分支），
  但**断点续传实际失效**，大文件中断就得从头来。记录下来。
- 若返回 **403** → 链接已过期（下载地址有效期很短）。客户端有换链逻辑，但要确认 TTL 实际是多久。

- [x] download-url 能拿到
- [x] Range 返回 206：**☑ 是** ☐ 否（否则续传失效）
      —— 2026-08-26 实测 `HTTP 206` + `Content-Range: bytes 0-1023/205818547`
- [x] 记录下载地址实际 TTL：**21600** 秒（6 小时，2026-08-26 实测）
      —— **比这一节原文假设的「有效期很短」宽松得多**。换链逻辑仍然要留（长视频 + 慢网仍可能超），
      但「下载中途 403」不该再当成首选怀疑对象

- [x] 该任务被重新领取并完成，而不是永久卡在 running

> 输出只有 `completed=0 failed=0 skipped=0`。这是租约机制**正常工作**的表现，不是卡死。

## 附 · 「现象相同、原因不同」速查

联调时最耗时的不是修 bug，而是**误判现象**。这几组值得先记住：

| 现象 | 可能原因 | 怎么区分 |
| --- | --- | --- |
| 资产列表为空 | ①策略兜底 deny 且无种子 ②会议真的没录制 ③服务账号 `id` 与规则 `subject_value` 对不上 ④命中的规则 `asset_types` 里没有这几类 | 查 `policy_rules` + `service_accounts.id`；换一场确定有录制的会议 |
| 只有 3 类资产、没有 AI 纪要 | ①STS 不可用（catalog 静默跳过 ai_*）②AI 纪要确实还没生成 | 看 preflight 第 7 项；查 `sts_tokens` 表有无有效 token |
| 认证失败但不知哪儿错 | 账号不存在/密钥错/已禁用/已过期 —— **有意合并为同一错误** | 直接查 `service_accounts` 表，别指望错误消息 |
| 下载中途 403 | 下载地址已过期（TTL 很短） | 正常，客户端会换链续传；确认最终文件完整即可 |
| 大文件中断后重下从 0 开始 | 对象存储不支持 Range（返回 200） | Stage 7 的 Range 检查 |
| 根目录 `bun test` 有 26 个失败 | 未设 `TEST_DATABASE_URL`（网关库测试） | 与客户端无关；只跑客户端用 `cd client && bun test` |
