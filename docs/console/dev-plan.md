## 0. 这份计划的粒度

**阶段级**，不是逐任务 TDD 计划。仓库的惯例是两层：

```
docs/roadmap.md            里程碑（M1…M6）
docs/console/dev-plan.md   ← 本文：阶段、依赖、并行波次、落点文件、规模
docs/superpowers/plans/    逐任务 TDD 计划，每个阶段开工前用 writing-plans 展开
```

六个阶段一次展开成逐步骤计划会得到几千行，且大半会在写到第三阶段时就过期。
**每个阶段开工前再展开。**

## 1. 三个决定（✅ 已定，2026-08-23）

### D1 · 控制台管理员怎么登录

**已定：账号密码，与企微身份解耦。明确不做企微登录。**

M2 确认的「企微账号、无独立体系、无 SSO」说的是**谁能导出数据**的身份映射，
不是**谁能进运维面板**。两者的人群和风险完全不同：

| | 导出身份 | 控制台管理员 |
| --- | --- | --- |
| 人数 | 全公司（受策略约束） | 1–3 人 |
| 用途 | 取数据 | 改规则、改授权、暂停清理 |
| 挂了会怎样 | 取不到数据 | **NAS 断连时进不去，唯一能阻止不可逆损失的开关按不了** |

最后一行是决定性的：控制台是**故障时才最需要用**的面板，把它的登录挂在另一个
可能同时挂掉的系统上是错的。独立账号（argon2id，复用 `auth/service.ts` 的哈希
方式），原型不用重画。

**企微扫码不做，也不留作后续选项。** 控制台的登录必须只依赖本系统自己的
数据库——多一条通道就多一个在故障时失效的可能，而这个面板的价值恰恰在故障时。
这一条同时写进 [`spec.md` §10 明确不做](spec.md#10-明确不做yagni)。

落点：`admin_accounts` 表 + `src/auth/admin.ts`（阶段 4 的 A1），argon2id 与会话
签发复用 `auth/service.ts` 与 `auth/tokens.ts` 的现成实现。原型的登录页不用改。

### D2 · 与 M5 桌面应用的关系

**已定：M5 无限期推迟，但不取消。**

桌面端原本的不可替代价值是「文件落在管理员自己的机器上」。这件事 **`mde` CLI
已经能做**，而且做得更好（可脚本化、可定时、无 GUI 依赖）。控制台补上「服务器
持续归档」之后：

```
服务器持续归档 + 到期治理   →  控制台
管理员本机按需导出          →  mde CLI
```

两个场景都有主了，桌面端夹在中间没有独占价值。不取消，是因为「给不用命令行的人
一个壳」仍是真需求——但那时它是 **C 方案（内嵌 webview 复用控制台前端）**，
成本低一个数量级。所以更该等控制台前端做完再说。

落点：`docs/roadmap.md` 的 M5 已标注推迟。在此期间「不用命令行的管理员」由控制台
覆盖，「要把文件落到本机」由 `mde` CLI 覆盖。

### D3 · 前端技术栈

**已定：React + Vite + TypeScript，`tokens.css` 原样引入，不套 UI 框架。**

原型是 vanilla JS，但它的状态密度——表格多选与跨页全选、右侧抽屉、规则编辑器的
条件构建器 + 实时影响预览、播放器与章节与转写的三处联动——手写会很快失控。

不套 Ant Design / MUI，是因为 `design-system.md` 已经是一套完整的令牌与组件语义，
再套框架等于同时维护两套设计系统，且框架的默认视觉会一路渗出来。

## 2. CLI 怎么整合

### 2.1 现状：两套东西各干各的

| | 网关 `src/` | CLI `client/` |
| --- | --- | --- |
| 运行在 | 服务器 | 管理员自己的机器 |
| 存储 | MySQL | SQLite（`bun:sqlite`） |
| 触发 | HTTP 请求 | 人敲命令 |
| 认证 | 发 token | 服务账号持 token |
| 干什么 | 把腾讯的东西**代理出去** | 把东西**拉到本地** |

控制台要的「服务器持续归档」是第三种形态：**跑在服务器上、写 MySQL、被调度器
触发、自己拉自己存**。它和 CLI 干的是同一件事（拉资产），只是宿主不同。

### 2.2 分三层整合

#### 第 1 层 · 引擎共用（代码级）

`client/` 里真正有价值的是**引擎**，不是 CLI 外壳。而它的三个外部依赖
**从第一天就是接口**：

```
GatewayClient   listMeetings / listAssets / getDownloadUrl
Store           claimNext / upsertAsset / markCompleted / …
Storage         appendChunk / finalize / ensureFreeSpace / …
```

`executor` 依赖的是 `Pick<GatewayClient, 'listAssets'>` 而不是具体实现。
**换宿主只需换这三个实现，引擎一行不改**——这是 M3 那份设计留下的最大红利，
现在正好兑现。

逐模块去留：

| `client/` 模块 | 服务端怎么处理 | 为什么 |
| --- | --- | --- |
| `domain/types.ts` | **原样复用** | 八类资产、文件名规则、扩展名归一化。控制台 spec §6.2 和它是同一份东西，**不能有第二份**（见 §5 冲突 C7） |
| `domain/readiness.ts` | 原样复用 | 资产就绪判定 |
| `domain/filename.ts` `domain/window.ts` | 原样复用 | |
| `downloader/` | **原样复用** | 断点续传、5 分钟链接到期换链。服务端拉 2GB 录像同样需要 |
| `executor/` | 复用逻辑，换 `Store` 实现 | 租约、重试上限、探测退避循环 |
| `discovery/` | 复用，换触发源 | 从「CLI 参数指定时间窗」变成「拉取规则决定」 |
| `storage/local.ts` | 复用为「本地保留区」 | NAS 适配器是它的兄弟实现，同一个 `Storage` 接口 |
| `store/db.ts`（SQLite） | **不复用** | 服务端用 MySQL，理由见下 |
| `gateway/client.ts`（HTTP） | **不复用** | 服务端在进程内直连 `catalog/` + `tencent/`，不自己 HTTP 调自己 |
| `cli/` `bin/` | 不复用 | CLI 外壳 |

**服务端为什么不能沿用 SQLite**：控制台的核心价值是「随时能回答为什么这场会议
这个程序取不到」。状态一旦分散在两个库，这个问题就答不出来。更硬的理由是
spec §7.2——NAS 断连时要**同时**清零保留窗口、撤下授权、把归档失败数从 1 改成 5，
这是跨表事务，必须在一个库里。

#### 第 2 层 · CLI 保留为独立工具（产品级）

**不废弃，定位改为「应急导出 + 引擎的第二宿主」。**

它继续用 SQLite + HTTP，和控制台各走各的。保留的三个理由：

1. **控制台或 NAS 挂掉时唯一的取数通道**——这正是它最该在的时候
2. M3.5 联调、以后每次排查上游变更，都靠它
3. 它是引擎正确性的活证据（58 个测试 + 一条真实链路）

#### 第 3 层 · CLI 反过来受控制台管辖（治理级）

`mde` CLI 用服务账号登录 —— **它本身就是控制台「采集授权」页里的一个采集程序**。
所以：

- 采集授权页应该能看到 `mde-cli` 这个程序，和「知识库索引器」并列
- 它取走的每一份资产**已经在 `audit_log` 里了**（`auth/service.ts` +
  `audit/recorder.ts` 一直在记）
- 这一层**不需要改 CLI 一行代码**，只需要控制台的审计读侧（G8）把它显示出来

这是整合方案里最便宜的一层，也最容易被漏掉。

### 2.3 一处必须显式处理的安全语义

服务端 worker 在进程内直连 `catalog/` + `tencent/`，**绕过了 `policy/engine.ts`**。
这不是疏漏，是正确的——但必须在代码里写明，否则将来一定有人当 bug「修」回去：

```
① 拉取      受「拉取规则」管       ← worker 走这条，与策略引擎无关
③ 采集权限  受「采集权限规则」管   ← 外部程序取数据时走，由策略引擎判
```

spec §1.4 说「采集权限规则是数据离开企业边界的唯一闸门」。worker 把数据从腾讯
拉进**企业内部**的归档区，没有跨企业边界，所以不该过那道闸门。
**闸门在出口，不在入口。**

落点：worker 入口函数上写明这段，并在 `spec.md` §1.4 补一句。

### 2.4 CLI 会不会和控制台重复下载

会，且是设计如此：服务器归档区一份、管理员机器一份。两者的 `storageRoot`、DB、
触发方式全独立，审计里靠 actor 区分。

**不做去重**——「管理员本机那一份」的全部意义就是**脱离服务器可用**。

风险从「一个管理员的一次导出」放大到「全公司会议的持续归档」。

| 任务 | 内容 | 落点 | 规模 |
| --- | --- | --- | --- |
| **E1** | 抽出共享引擎包 | 移动 `client/src/{domain,downloader,executor,discovery,storage}` → `packages/engine/`；根 `package.json` 加 `workspaces` | 中 |

**E2 的难点只有一处**：`claimNext` 的租约领取。SQLite 单进程靠一条

| 任务 | 内容 | 落点 | 规模 |
| --- | --- | --- | --- |
| **R1** | 三栈规则引擎 | 重写 `src/policy/`；`migrations/003_*.sql` 加 `kind` 列并换条件表示法 | 大 |
| **R2** | 影响预览纯函数 | `src/policy/preview.ts`，**不落库** | 中 |
| **R3** | 逐会议 × 逐程序授权 + 人工改写 | `meeting_grants` / `meeting_overrides` 表 | 中 |

**R1 是本阶段最大的一块，语义必须逐字实现（spec §5）。** 现有引擎的排序方向与
spec 相反（§5 冲突 C1）——这不是「改个符号」：旧数据是按旧语义写的规则，换方向后
判定会翻转。迁移脚本要么把现有规则的 priority 重排，要么显式声明现有规则集为空。

**R3 的「人工改写优先于所有规则」必须落在引擎之外**：引擎只管规则，改写是引擎
结果之上的覆盖层。混进引擎会让影响预览算不准——spec §5.4 要求把改写过的会议
排除在「会被改变」之外。

## 5. 开工前必须消解的七处冲突

这些不是缺口，是**规格与现有实现互相矛盾**。留着不解，两边会各按自己的理解写，
最后在联调时才发现。

| # | 冲突 | 现状 | 建议 | 状态 |
| --- | --- | --- | --- | --- |
| **C1** | **规则优先级排序方向相反** | `policy/engine.ts` 是 `a.priority - b.priority` **升序**取第一条；spec §5.1 要求**降序** | 按 spec 改成降序，**并写迁移重排现有规则**。同一批数据两套语义会得出相反结论 | 📌 已写进 spec §5.1，待 R1 实现 |
| **C2** | 同优先级的平局规则未定义 | 现有引擎「同优先级 deny 优先」；spec 只说「第一条命中的说了算」，没说平局 | 补进 spec §5.1：同优先级按 `id` 升序（建得早的先） | ✅ 已定 |
| **C3** | 规则主体语义不同 | 现有 `subject_type/subject_value` 只按 **user** 匹配；控制台三栈里 fetch/archive **无主体**（系统级），allow 栈的主体是**采集程序**不是人 | `subject_type` 增加 `program` 取值；fetch/archive 两栈主体列留空并在引擎里显式忽略 | ✅ 已定 |

| **C6** | **`dur` 会议时长其实可算，但被过期注释封着** | `tencent/records.ts` 的 `meetingEndTime()` 已从 `record_files[].record_end_time` 聚合出真实结束时间（`d191f5b`，2026-08-21）；但 `domain/types.ts` 上「恒等于 startTime、本次未做」的注释停在 `f00406b`（2026-07-21），`policy/expr.ts` 也据此仍拒绝 `end_time` | 清掉过期注释，在 `expr.ts` 开放 `end_time`；**M3.5 用真实响应确认 `record_end_time` 确实存在**——否则会回落到 `media_start_time`，时长恒为 0 | 🟡 注释已清，字段待 M3.5 |
| **C7** | **资产类型出现了第三套名字** | `spec.md` §6.2 的「腾讯侧类型」列有两行与 M3.5 实测不符：`transcript` 实际是 `meeting_summary`，`ai_transcript` 实际是 `ai_meeting_transcripts` | 改 spec，**控制台直接用 `ASSET_KEY_TO_GATEWAY_TYPE` 这一份映射** | ✅ 已定 |

C7 值得多说一句：同一批八类资产现在有三套叫法——

```
控制台原型   summary / transcript / speaker / topic / aitr / digest / video / audio
客户端       ai_minutes / transcript / ai_speaker_minutes / … （AssetKey）
```

`download_address`，实际 emit 的是 `video`，只有 video/audio 两项不同——这种

最后按 deadline 静默放弃。经过在 `client/src/domain/types.ts` 里详细记过。

**第三套名字现在还只存在于原型 HTML 和 spec 里，现在删掉最便宜。**

## 6. 规模与风险

| 阶段 | 规模 | 主要成本 |
| --- | --- | --- |
| 0 前置 | 小 | 联调需要真实凭证与环境 |
| 1 引擎重构 | 中 | E2 的 MySQL 队列并发正确性 |
| 2 流水线 | 大 | NAS 网络中断处理 + **不可逆删除**的正确性 |
| 3 规则授权 | 大 | R1 语义逐字实现 + 迁移不得改变现有判定 |
| 4 控制台 API | 大 | A2 一行会议要拼四个维度 |
| 5 前端 | 大 | 六页 + 五个缺口 |

### 最高风险：阶段 2 的 P3（到期清理）

它是全系统唯一执行**不可逆删除**的代码。三条硬要求：

1. **删之前当场重新校验** NAS 上那份文件的哈希与库里记录一致——不是查「归档任务
   报过成功」，是**重新读一遍算一遍**
2. **「暂停到期清理」开关必须持久化**，不能是内存标志。NAS 断连通常伴随重启或
   切换，内存标志会在最需要它的时候消失
3. **必须有 dry-run，且默认先跑 dry-run**

### 次高风险：阶段 3 的 R1 迁移（C1）

它会**静默改变现有规则的判定结果**。要求：迁移跑完后，拿迁移前的规则集与会议集
重算一遍，**判定结果必须逐条一致**；不一致的要能列出来交人工确认，而不是让脚本
自己决定。
