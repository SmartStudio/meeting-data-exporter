## 1. 三个决定（已定，2026-08-23）

### D1 · 控制台管理员怎么登录

已定：账号密码，与企微身份解耦。明确不做企微登录。

M2 确认的「企微账号、无独立体系、无 SSO」说的是谁能导出数据的身份映射，
不覆盖谁能进运维面板。两者的人群和风险完全不同：

| | 导出身份 | 控制台管理员 |
| --- | --- | --- |
| 人数 | 全公司（受策略约束） | 1 到 3 人 |
| 用途 | 取数据 | 改规则、改授权、暂停清理 |
| 挂了会怎样 | 取不到数据 | NAS 断连时进不去，唯一能阻止不可逆损失的开关按不了 |

最后一行是决定性的：控制台在故障时最需要用，把它的登录挂在另一个可能同时挂掉的
系统上是错的。独立账号（argon2id，复用 `auth/service.ts` 的哈希方式），原型不用重画。

企微扫码不做，也不留作后续选项。控制台的登录只依赖本系统自己的数据库。多一条
通道就多一个在故障时失效的可能，而这个面板要在故障时可用。这一条同时写进
[`spec.md` §10 明确不做](spec.md#10-明确不做yagni)。

落点：`admin_accounts` 表 + `src/auth/admin.ts`（阶段 4 的 A1），argon2id 与会话
签发复用 `auth/service.ts` 与 `auth/tokens.ts` 的现成实现。原型的登录页不用改。

### D2 · 与 M5 桌面应用的关系

已定：M5 无限期推迟，但不取消。

桌面端原本的不可替代价值是「文件落在管理员自己的机器上」。这件事 `mde` CLI
已经能做，而且可脚本化、可定时、不依赖 GUI。控制台补上「服务器持续归档」之后：

```
服务器持续归档 + 到期治理   →  控制台
管理员本机按需导出          →  mde CLI
```

两个场景都有了承接者，桌面端没有独占价值。不取消是因为「给不用命令行的人
一个壳」仍是真需求，届时按 C 方案做（内嵌 webview 复用控制台前端），
成本低一个数量级，所以更该等控制台前端做完再说。

落点：`docs/history/roadmap.md` 的 M5 已标注推迟。在此期间「不用命令行的管理员」由控制台
覆盖，「要把文件落到本机」由 `mde` CLI 覆盖。

### D3 · 前端技术栈

已定：React + Vite + TypeScript，`tokens.css` 原样引入，不套 UI 框架。

原型是 vanilla JS，但它的状态密度很高：表格多选与跨页全选、右侧抽屉、规则编辑器的
条件构建器加实时影响预览、播放器与章节与转写的三处联动。这些手写会很快失控。

不套 Ant Design / MUI，是因为 `design-system.md` 已经是一套完整的令牌与组件语义，
再套框架等于同时维护两套设计系统，且框架的默认视觉会一路渗出来。

## 2. CLI 怎么整合

### 2.1 现状：两套东西各干各的

| | 网关 `src/` | CLI `client/` |
| --- | --- | --- |
| 运行在 | 服务器 | 管理员自己的机器 |
| 存储 | MySQL | SQLite（`bun:sqlite`） |
| 触发 | HTTP 请求 | 人敲命令 |
| 认证 | 发 token | 服务账号持 token |
| 干什么 | 把腾讯的东西代理出去 | 把东西拉到本地 |

控制台要的「服务器持续归档」是第三种形态：跑在服务器上、写 MySQL、被调度器
触发、自己拉自己存。它和 CLI 干的是同一件事（拉资产），只是宿主不同。

### 2.2 分三层整合

#### 第 1 层 · 引擎共用（代码级）

`client/` 里有复用价值的是引擎，不含 CLI 外壳。它的三个外部依赖从第一天就是接口：

```
GatewayClient   listMeetings / listAssets / getDownloadUrl
Store           claimNext / upsertAsset / markCompleted / …
Storage         appendChunk / finalize / ensureFreeSpace / …
```

`executor` 依赖的是 `Pick<GatewayClient, 'listAssets'>`，不依赖具体实现。
换宿主只需换这三个实现，引擎一行不改。这是 M3 那份设计留下的红利，现在正好兑现。

逐模块去留：

| `client/` 模块 | 服务端怎么处理 | 为什么 |
| --- | --- | --- |
| `domain/types.ts` | 原样复用 | 八类资产、文件名规则、扩展名归一化。控制台 spec §6.2 和它是同一份东西，不能有第二份（见 §5 冲突 C7） |
| `domain/readiness.ts` | 原样复用 | 资产就绪判定 |
| `domain/filename.ts` `domain/window.ts` | 原样复用 | |
| `downloader/` | 原样复用 | 断点续传、5 分钟链接到期换链。服务端拉 2GB 录像同样需要 |
| `executor/` | 复用逻辑，换 `Store` 实现 | 租约、重试上限、探测退避循环 |
| `discovery/` | 复用，换触发源 | 从「CLI 参数指定时间窗」变成「拉取规则决定」 |
| `storage/local.ts` | 复用为「本地保留区」 | NAS 适配器是它的兄弟实现，同一个 `Storage` 接口 |
| `store/db.ts`（SQLite） | 不复用 | 服务端用 MySQL，理由见下 |
| `gateway/client.ts`（HTTP） | 不复用 | 服务端在进程内直连 `catalog/` + `tencent/`，不自己 HTTP 调自己 |
| `cli/` `bin/` | 不复用 | CLI 外壳 |

服务端不能沿用 SQLite 的理由：控制台的核心价值是「随时能回答为什么这场会议
这个程序取不到」。状态一旦分散在两个库，这个问题就答不出来。更硬的理由是
spec §7.2，NAS 断连时要同时清零保留窗口、撤下授权、把归档失败数从 1 改成 5，
这是跨表事务，必须在一个库里。

#### 第 2 层 · CLI 保留为独立工具（产品级）

不废弃，定位改为「应急导出 + 引擎的第二宿主」。

它继续用 SQLite + HTTP，和控制台各走各的。保留的理由：

1. 控制台或 NAS 挂掉时，它是唯一的取数通道
2. M3.5 联调、以后每次排查上游变更，都靠它
3. 它是引擎正确性的证据（58 个测试加一条真实链路）

#### 第 3 层 · CLI 反过来受控制台管辖（治理级）

`mde` CLI 用服务账号登录，它本身就是控制台「采集授权」页里的一个采集程序。
所以：

- 采集授权页应该能看到 `mde-cli` 这个程序，和「知识库索引器」并列
- 它取走的每一份资产已经在 `audit_log` 里（`auth/service.ts` +
  `audit/recorder.ts` 一直在记）
- 这一层不需要改 CLI 一行代码，只需要控制台的审计读侧（G8）把它显示出来

这一层成本最低，也最容易被漏掉。

### 2.3 一处必须显式处理的安全语义

服务端 worker 在进程内直连 `catalog/` + `tencent/`，绕过了 `policy/engine.ts`。
这是有意为之，必须在代码里写明，否则将来会有人当 bug「修」回去：

```
① 拉取      受「拉取规则」管       ← worker 走这条，与策略引擎无关
③ 采集权限  受「采集权限规则」管   ← 外部程序取数据时走，由策略引擎判
```

spec §1.4 说「采集权限规则是数据离开企业边界的唯一闸门」。worker 把数据从腾讯
拉进企业内部的归档区，没有跨企业边界，所以不该过那道闸门。闸门设在出口。

落点：worker 入口函数上写明这段，并在 `spec.md` §1.4 补一句。

### 2.4 CLI 会不会和控制台重复下载

会，且是设计如此：服务器归档区一份、管理员机器一份。两者的 `storageRoot`、DB、
触发方式全独立，审计里靠 actor 区分。

不做去重。「管理员本机那一份」的意义就是脱离服务器可用。

R1 是本阶段最大的一块，语义必须逐字实现（spec §5）。现有引擎的排序方向与
spec 相反（§5 冲突 C1），改动不止于换个符号：旧数据是按旧语义写的规则，换方向后
判定会翻转。迁移脚本要么把现有规则的 priority 重排，要么显式声明现有规则集为空。

> R1 的落地结论（2026-08-25）：生产库 `policy_rules` 实测只有 1 行，
> C1 的排序风险归零（单条规则命中就是它、不命中走兜底，两套语义结论相同）。
> 迁移把现有行全量搬进 `policy_rules_legacy` 后清空 `policy_rules`，
> 不自动转换语义。旧规则的主体是人，新 allow 栈的主体是采集程序
> （`service_accounts.id`），两者之间没有机械的对应关系。
>
> 连带的语义变更：企微用户走到采集权限栈一律被显式拒绝（登录的是人，
> 不是采集程序），`ActorIdentity` 因此带上了 `programId`。本次部署本就没启用
> 企微登录（四条设备流程路由返 501），影响面只在测试里。

R3 的「人工改写优先于所有规则」必须落在引擎之外：引擎只管规则，改写是引擎
结果之上的覆盖层。混进引擎会让影响预览算不准，spec §5.4 要求把改写过的会议
排除在「会被改变」之外。

> R3 的落地结论（2026-08-26）：覆盖层（`src/policy/override.ts`）本身之外，
> 还必须把它接到每一条判定路径上，否则 spec §5.4 落不到实处：
>

## 6. 规模与风险

| 阶段 | 规模 | 主要成本 |
| --- | --- | --- |
| 0 前置 | 小 | 联调需要真实凭证与环境 |
| 1 引擎重构 | 中 | E2 的 MySQL 队列并发正确性 |
| 2 流水线 | 大 | NAS 网络中断处理 + 不可逆删除的正确性 |
| 3 规则授权 | 大 | R1 语义逐字实现 + 迁移不得改变现有判定 |
| 4 控制台 API | 大 | A2 一行会议要拼四个维度 |
| 5 前端 | 大 | 六页 + 五个缺口（实际交付 8 个页面 + 11 个任务，见 §3 阶段 5） |

### 最高风险：阶段 2 的 P3（到期清理）

它是全系统唯一执行不可逆删除的代码。硬要求：

1. 删之前当场重新校验 NAS 上那份文件的哈希与库里记录一致，要重新读一遍算一遍，
   不能只查「归档任务报过成功」
2. 「暂停到期清理」开关必须持久化，不能是内存标志。NAS 断连通常伴随重启或
   切换，内存标志会在最需要它的时候消失
3. 必须有 dry-run，且默认先跑 dry-run

### 次高风险：阶段 3 的 R1 迁移（C1）

它会静默改变现有规则的判定结果。要求：迁移跑完后，拿迁移前的规则集与会议集
重算一遍，判定结果必须逐条一致；不一致的要能列出来交人工确认，不让脚本自己决定。

### 7.1 为什么下一步是部署（三条实测判据）

① 镜像里没有 `packages/`，连网关自己都 import 不动。

`package.json`。而 `src/` 下有 19 个文件 import `@yaowu/mde-engine`，其中是值导入

```

```

所以后果比「worker 起不来」更大：`src/index.ts → http/router.ts →
handlers/console/meetings.ts → @yaowu/mde-engine` 是一条模块加载期就走通的链，
按当前 `Dockerfile` 构出来的镜像网关自己也起不来。deps 阶段又只

`workspaces: ["client", "packages/*"]` 的成员一个都不在场，`@yaowu/mde-engine`

② 镜像里没有 `console/`，网关也不 serve 静态文件。
`src/http/router.ts` 与 `src/index.ts` 里没有任何 static / `Bun.file` 的痕迹，
`docs/deploy.md` 里没有一句控制台部署。合起来是：控制台前端从没被任何人打开过，
