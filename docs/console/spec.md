## 1. 产品模型

一句话：把腾讯会议的录制与纪要收进来，归档进 NAS，在本地留一个窗口期，
期间按规则和授权让外部程序取走；窗口期一到删本地文件，只留记录和 NAS 路径。

### 1.1 四个阶段

```
腾讯会议
   │
   │ ① 拉取        由「拉取规则」决定拉哪些会议、拉哪几类资产
   ▼
本系统本地
   │
   │ ② 归档 NAS    由「归档规则」决定进 NAS 的哪个目录
   ▼
NAS（长期唯一存放地）
   │
   │ ③ 本地保留 30 天    自归档成功日起算，不是自会议日起算
   │    这期间外部程序可以取
   ▼
   ④ 到期            删本地文件，保留数据库记录 + NAS 路径
```

保留天数是 `system_settings` 里的可改设置（`GET /api/v1/admin/storage` 的
`retention.defaultDays`），30 天是没配过时的默认值。

### 1.2 NAS 是主存储，不是备份

这一点决定了所有告警等级：

> 没有归档成功的会议，本地保留期一到就彻底没有了。

腾讯会议侧的录制有自己的留存策略，不能假定它一直在。所以：

- 归档失败是本系统最高级别的告警，红色，且在会议列表的分诊条里单列一格
- NAS 断连时，控制台提供「暂停到期清理」的应急开关（见 §7.2）。那是唯一能
  阻止不可逆损失的动作，所以它出现在告警条本身上，不藏在设置里

### 1.3 外部程序真能取到 = 三个「与」

```
有授权（这场会议授权给了这个程序）
  且  在保留期内（本地文件还没被删）
  且  规则允许采集（权限规则栈判定 allow）
```

三个条件缺一不可，且分别由不同的人、在不同的页面维护。界面必须随时能回答
「为什么这场会议这个程序取不到」，所以每场会议的详情里都有逐阶段的判定理由
（`why.fetch` / `why.archive` / `why.allow`）。

网关每次取数时，第一个和第三个「与」都在 `AccessGate` 里判（`src/policy/access.ts`
加 `src/policy/grant.ts`，阶段 6，2026-09-03）。此前它只判第三个：只要库里有一条
allow 规则，没有任何授权的采集程序照样列得出会议、拿得到下载地址，而采集授权页
按授权行枚举、显示「0 场对它开放」，控制台说 0 而程序实际取得到。

第二个「与」在网关仍然不作为判定条件。2026-09-20 起网关按 `meeting_assets.target_path`
从本地归档直出文件，本地被清理后回退 `archived_assets.nas_path` 从 NAS 直出，
所以本地已到期的会议只要 NAS 那份还在就仍然取得到。详情见 §11 第 10 行。

### 1.4 数据出企业边界的唯一闸门

采集权限规则是数据离开企业边界的唯一闸门。任何新增的出境路径（例如把会议
内容送给大模型做问答）都必须走同一道闸门，不能从别的页面另开一个口子。

原型的内容预览页右下角为「向这场会议提问」留了位置，本系统刻意没有实现：那是一条
新的出境路径，真要接就当一个采集程序来管，走接入向导拿凭据、受规则和授权约束、
每次问答记一条审计。

这条理由记在这里和 §10，不写在界面上（2026-08-28）。此前内容预览页右下角
渲染着一整块「向这场会议提问 · 刻意不做」，两段散文解释一个不存在的输入框为什么
不存在。它和 §11 第 7 行的「撤销归档」属于同一类问题：在界面上放一条只对开发者有意义的
产品笔记。控制台上不再出现这一块，连那个禁用的输入框也不画。一个点不动的输入框
会让人以为这个功能即将上线，而这里的实际情况是决定还没做，不是工期还没到。

## 2. 角色与权限

| 角色 | `role` | 能做什么 | 状态 |
| --- | --- | --- | --- |
| 数据管理员 | `admin` | 全部：改规则、改授权、延长保留、手动触发任务、看内容 | 已实现 |
| 只读角色 | `readonly` | 只能看：全部 GET，加上「改自己的密码」「登出」两条 | 已实现（阶段 5） |

M2 已确认「仅管理员可导」，所以控制台不面向全员。用户菜单里那一行随角色变：
`admin` 是「数据管理员 · 可改规则与授权」，`readonly` 是「只读账号 · 只能查看，不能改」。

权限由后端执行。路由表共 54 条，其中 `/api/v1/admin/*` 41 条、非 GET 的
24 条。除下面三条白名单外的 21 条写端点逐条拒绝只读账号（403 `readonly_role`，
带一句可以直接显示的中文）。守它的是 `tests/http/console-readonly.test.ts`，
它遍历路由表，任何一条新增的非 GET admin 端点只要没挡住只读账号就会红。
前端把对应的入口禁用掉（禁用而不隐藏，隐藏会让只读用户以为这个功能不存在），
但那一层只是别让人白点，绕过界面发来的写请求由后端那条 403 挡住。

`role` 读不出来时按 `readonly` 处理。后端认不出的取值在服务端就折成 `readonly`；
前端在 `GET /auth/me` 少了这个键时同样落到只读一侧。两个方向的代价不对称：
落错成只读只是多点一次刷新，落错成管理员是让人以为自己改成了、而后端其实拒了。
判断方向是「只有明确是 `admin` 才放行」的白名单，加第三个角色时不会被静默当成管理员。

三条非 GET 但允许只读：`POST /auth/login`（登录时还没有角色可言）、
`POST /auth/logout`（撤销的是自己的会话，挡住它等于只读账号退不出登录）、
`POST /auth/password`（改的是自己的凭据，挡它防不住任何越权，
只会让怀疑密码泄露的人无法自救）。

账号的增删改有端点（`POST` / `PATCH` / `DELETE /api/v1/admin/accounts[/:id]`），
控制台还没有账号管理页，改角色这一步目前只能走接口。403 的提示语里写明了这一点。

管理员查看会议内容会留痕。尤其是被规则禁止采集的会议，管理员仍然能看
（他要判断这条规则拦对了没有），但顶部挂琥珀警示条，且这次查看进审计日志。

## 3. 信息架构

左栏六项，外加一个不占导航的内容预览页。下表七行，最后一行的 `preview` 不进左栏。

| 页面 | `data-view` | 回答什么问题 |
| --- | --- | --- |
| 会议记录 | `meetings` | 每场会议现在处在哪个阶段、还剩几天、谁能取 |
| 采集授权 | `consumers` | 每个外部程序现在实际能取到多少东西 |
| 自动规则 | `rules` | 拉什么、归档到哪、放行什么 |
| 定时任务 | `jobs` | 五个任务跑得怎么样、失败项在哪 |
| 归档存储 | `storage` | NAS 还剩多少、保留窗口里有多少 |
| 操作审计 | `audit` | 谁在什么时候取走了什么 |
| 内容预览 | `preview` | 这场会议里到底讲了什么（从会议记录点标题进入） |

前端路由是八条（`console/src/app/routes.tsx`）：上表七条加 `/login`。
`/login` 刻意是 `/` 的兄弟节点、不挂在 `AppShell` 底下，它没有左栏和顶栏，
且必须在「判断有没有登录」完成之前就能渲染。

左栏「定时任务」右侧有一颗红点，只在有你还没看过的失败项时亮：打开定时任务页、
失败列表读完就算看过，红点灭；之后出现比那一刻更新的失败（含一条旧失败自动重试又失败）
才再亮。它不显示条数，条数在左栏底部的状态摘要里（「N 项需要处理」），同一个数字不在两处显示。
「看过」的记号是最新一条失败的 `lastFailedAt`，存在浏览器本地（`console/src/app/failuresSeen.ts`）。
左栏读的系统状态在换栏目、标签页回到前台时重读一次，重读期间上一份数据留在屏幕上；不轮询。

### 3.1 页头这条带子

七页共用 `ui/PageShell` 的页头：一句说明（这一页回答什么问题）加右侧主操作。
可见的页面标题不在这里，在顶栏。

- 页头按它装的东西高，装不下东西就没有页头。说明和主操作都没有的页面
  （会议记录、归档存储）不画那条带子，内容直接从内容区的上留白开始。
  1440 实测：改前会议记录与归档存储在顶栏底下空着 36px 什么都没有，而有说明的
  页面同一位置是 64-86px、装着一句话。空白高度是「这一页恰好有没有副标题」的
  副产品，不是一条规则。改后七页首个元素一律距顶栏 16px。
- 不为了把带子填满而编一句说明。一句只为撑住版面而写的话，读者要读，却得不到任何信息。没有说明就不画带子。
- 一个控件不单独占一条带子。内容预览的「返回会议列表」曾经是页头里唯一
  的东西，右对齐，左边九成宽是空的，而这一页正下方还有它自己的抬头（会议
  标题加时间加判定标记），两条抬头上下摞着。它现在是内容区的第一行，左对齐。

### 3.2 起笔对齐

七页内容区第一个着色像素都落在顶栏底下 14-22px 这条带子里，由
`npm run a11y` 的检查 6 逐页量像素守着（每页量两次：全宽一次、左侧文字栏一次）。

- 内容区上留白是 `--s-5`（16px）。以边框或底色开头的页面（归档存储的卡片、
  采集授权右侧那颗按钮）起笔就是 16；以文字开头的多出半行距，落在 19-20。
- 对齐的是文字，不是内边距盒。第一个控件自带的上内边距要用等量的负外边距
  抵掉，分诊条（`.seg` 8px）和预览页返回链接（`.back` 6px）都是这么做的，
  与分诊条第一段那句 `padding-left: 0`（让第一段跟内容左边缘对齐）是同一件事，
  只是换了个轴。挪的是整条的位置，不是它内部的几何，那点内边距还在撑高度和
  点击区域。
- 页头里的说明句与右侧主操作按钮顶对齐（`align-items: flex-start`）。两端
  相距一千多像素，没人会去比它们的垂直居中，看得见的是各自离内容上边缘多远。
  底对齐或居中都会把 22px 的说明句往下压（实测采集授权 26px 对自动规则 19px，
  同一句话在两页高低不一）。
- 这条规则被违反过两次，两次元素几何都是对的：一次是空页头照发 20px 下外边距
  （盒顶在 16，底下 20px 是空的），一次是控件自带上内边距（盒顶在 16，起笔在
  26/28）。所以门禁量像素，不量盒顶，量盒顶的门禁两次都会报通过。

## 4. 逐页说明

### 4.1 登录

![登录](screens/01-登录.webp)

账号加密码加「记住此设备 30 天」。仅限内部管理员，无自助注册、无找回密码
（文案明说「忘记密码请联系系统管理员」）。

这是独立于企微的账号体系（D1，2026-08-23），理由见 §10。

- 报错行是表单级的（「账号或密码错误」故意不说是哪个字段错了），常驻占位，
  避免出错时表单跳一行。它排在「登录」按钮之后，不夹在勾选框和按钮中间
- 截图里卡片底部那行四阶段 chip（`• 拉取 • 归档 NAS • 保留 30 天 • 授权采集`）
  已经删掉。它不接任何状态也点不动，而其中「保留 30 天」会撒谎：真实的保留天数
  来自 `system_settings`，管理员改成 60 天的那一刻这行字就开始骗人，而登录页没有
  会话、拿不到也不该拿这个设置。同批删掉的还有 72px 的占位标志方块与
  「仅限公司内部管理员使用」一句
- 留下的「忘记密码请联系系统管理员」在卡片之外。这一页没有找回密码的控件，
  也不会有，没有这句话的人只能在页面上找一个不存在的链接

**登录之后：用户菜单**（顶栏右上角，阶段 5 补齐，原 §11 缺口 5）。里面是当前账号名
（来自 `GET /auth/me`，不是写死的）、角色那一行（见 §2）、以及修改密码与
退出登录两个入口。

修改密码要填当前密码。只凭浏览器里那张会话 cookie 就能改密码，等于一次 XSS
就能永久接管账号。改完之后这个账号在其它设备上的会话会被吊销，当前这一条保留
（否则改完密码立刻把自己踢下线）；界面上要把被踢下线的会话数说出来，
0 也要说（「没有别的设备在登录」是一个结论，不是留白）。密码长度门槛与建号
那条路径共用同一份校验，前端不抄一个数，不够长时后端会说要几位。

### 4.2 会议记录（主页面）

![会议记录](screens/02-会议记录.webp)

**分诊条**（五格，每格可点即筛选）把「现在有什么需要处理」压成一行：

| 格 | 含义 | 颜色 |
| --- | --- | --- |
| 归档失败 | 到期会永久丢失 | 红 |
| 7 天内到期 | 过期后须去 NAS 取 | 琥珀 |
| 待授权 | 准许采集但没给程序 | 中性 |
| 处理中 | 拉取或归档进行中 | 中性 |
| 仅存 NAS | 本地已清理 | 中性 |

这一排只有两个颜色。「待授权」此前是品牌蓝，蓝在这一页有另一个含义（数据可被取走），
两个意思撞在一起，所以它和另外两段一样改成中性。计数读不到时不许显示 0，
「不知道有几场归档失败」与「没有归档失败」是两件事；同时也不隐藏这一格。

**表格列**：

| 列 | 内容 | 说明 |
| --- | --- | --- |
| 会议记录 | 标题 + 会议号 + 时间 | 标题是按钮，点进内容预览 |
| 主持人 | | |
| 资产 | `已拿到/应有` | 如 `19` 或 `7/19`（部分失败）或 `0/19` |
| 拉取 · 归档 | 两个圆点 + 连线 | 圆点即开关，点一下就能重跑该阶段 |
| 本地保留 | 进度条 + 剩余天数 | hover 出现「+30 天」按钮 |
| 已授权给 | 程序 pill，可加可删 | `+ 授权给…` 打开程序选择弹层 |

- 批量：勾选后底部浮出批量条（授权 / 延长 / 重跑）
- 跨页全选有逃生门：勾表头只选本页，要选全部得再点一次，且明说总数
- 人工改写优先于所有规则，改写过的行有标记

### 4.3 会议详情（右侧抽屉）

![会议详情抽屉](screens/03-会议详情抽屉.webp)

四段，对应产品模型的四个阶段，每段带判定理由：

1. 拉取：状态 + 是哪条规则决定的 + 五类资产各自的格式数与体积 + 「撤销拉取」
2. 归档到 NAS：NAS 路径（可复制）+ 归档时间 + 体积 + 「撤销归档」<sup>[1]</sup>
3. 本地保留：大号剩余天数 + 归档日/到期日 + 「延长 30 天」
4. 采集授权：已授权程序 + 是哪条权限规则放行/禁止的

底部是这场会议的操作历史（谁在什么时候取走了什么）。

关于这段历史的三条（2026-08-31，用户报「有很多重复的数据」之后定）：

- 每一行要说得出「看/取的是哪一份」。原来的行是 `actorId · 动作名 · 结果`，
  同一次打开预览页产生的四条（资产索引 / 时间轴 / 纪要 / 逐字稿）渲染成一模
  一样的一句话。区分字段一直在 `audit_log.detail` 里，只是没人用。机器名
  （`content:ai_minutes`）在读侧翻成 §6.2 那张表上的中文，认不出的原样带出
- 发起者显示人名，由 `admin_accounts` 解析。查不到时退回显示 id，
  不许拿 id 冒充人名，同「不拿会议 id 冒充标题」「不拿 userid 冒充主持人」
- 连续且逐字相同的行折成一行，右侧写 `×N`，时刻写成区间。折叠不等于去重：
  次数与时间跨度都必须留在界面上，少一个就等于把审计记录改写掉。
  §4.10 的操作审计页仍然不折，那一页是总账，每行都能展开看自己的
  `detail` 与规则快照，折叠之后「展开的是哪一行」当场答不上来；抽屉是一场会议的
  摘要，没有那个能力可毁

> <sup>[1]</sup> 「撤销归档」= 只撤记录，NAS 副本保留（2026-08-25 定）。
>
> 本文原先没有定义过这个动作的语义。两个选项的后果差距很大：删掉 NAS 副本是不可逆的，
> 而 §1.2 已经写明 NAS 是主存储不是备份。一旦本地保留窗口也已过期，撤销归档就等于
> 永久销毁这场会议的全部资产。按钮看起来只是「重来一次」，实际后果不止于此。
>
> 所以定为保留副本：撤销归档是可逆动作，不需要二次确认，也不走 §4.9 那套删除前的
> 哈希重校验。代价是归档记录与 NAS 实际文件会不一致，NAS 上会留下没有记录指向的孤儿文件；
> 重新归档时必须能正确处理「目标文件已存在」。清理孤儿文件是另一件事，不在本动作范围内。
>
> 对应 [用户故事 US-2.5](../superpowers/specs/2026-07-20-user-stories.md)，目前 0 实现，
> 控制台不放这个按钮，见 §11 第 7 行。

它是三个「与」条件求交之后的实际结果，不是管理员填进去的配置值。快到期的会额外用琥珀标出

凭据明文只出现一次，与 `scripts/seed-dev.ts` 的服务账号行为一致（库里只存
argon2id 哈希）。这一点必须在后端保持。

**卡片上还有两个动作**（阶段 5 补齐，原 §11 缺口 4）：

- 停用 / 启用。停用立刻生效，包括那个程序手上已经签发、还没过期的访问令牌，
  判定在 `AccessGate` 每一次取数时做，不是只在拿凭据换令牌那一层。停用
  不删任何授权：它是可逆动作，「停用再启用」不该变成一次不可逆的数据丢失。
- 轮换凭据。旧凭据当场失效，新明文只显示这一次（服务端只存哈希，
  没有也不会有「再看一次」的端点，那等于把哈希存储的意义抵消掉）。所以那一屏
  要勾一个「我已经保存好了」才关得掉，不勾就关会被再问一遍。

卡片上还有一个开关：自动授权。

一天新进来十几场会议，规则栈早就判得出「这个程序准不准采集它们」，可授权仍然要人
一场一场点。判定已经自动了，写授权这一步还是人工。这个开关补的就是这一步：开了之后，一个
后台任务（§4.8 任务五）每 5 分钟把该给的真的写进 `meeting_grants`。写出来的是
和人点出来的一模一样的授权行，清单、网关闸门、审计、批量收回全部原样能用；区别只在
审计里那条记录的操作者是「系统 · 自动授权」而不是某个人。

**候选判据**（四条全中才授权，一条不满足就不授权）：

1. 本地文件还在，与 §1.3 第二个「与」同一判据：归档行没被清理，或者本地还有
   下载完成的资产。还没归档但文件已经在本地的新会议算数，那正是要覆盖的那一批
2. 采集权限规则（含单场人工改写）判「准许」，判定一个字都不改，与网关那一侧
   跑的是同一段代码
3. 尚无生效授权，已经授权过的不动它，免得把管理员手工收窄过的范围改回去
4. 从未被人工撤销过，见下面第二条规矩

**三条规矩：**

- 停用的程序整个跳过。停用是「先别取」，不该在停用期间替它堆授权。
- 人工撤销过的会议不再自动补回。只要这个 (会议, 场次, 程序) 有过一条撤销记录，
  自动授权就跳过它，人的决定压过开关。没有这一条的话，撤销在界面上生效几分钟，
  下一轮自动写回来，管理员再撤一次，如此往复，而两边都不报错。想让它重新参与，
  路径是人工重新授权一次。
- 关掉开关不收回已有授权。可逆动作不该带不可逆后果：关开关时把几十上百场
  一并撤掉，等于让一次「先别自动加新的了」变成一次不可逆的批量撤销。要收回请去
  会议记录页批量收回，那条路上管理员看得见自己要撤的是哪些。

**资产范围**可以一起设（不填 = 不额外限制，以规则判定为准；填了就是白名单）。
改范围只对之后写出去的授权生效，已经写出去的授权行一个字都不改，要改那些
同样去会议记录页。空数组不接受（后端 400）：「什么都不授权的自动授权」写出来的
每一行都取不到任何东西，而且会因为「已有生效授权就跳过」永远挡住这场会议
日后被正确地自动授权。

停用的程序，那句蓝底的话换成「已停用 · 现在 0 场会议对它开放」。
清单端点算的是 授权 ∩ 保留期 ∩ 规则，不看 `enabled`，所以它对一个停用的程序
照样算得出「N 场可取」，而网关那一侧会拒。那正是 §1.3 要防的漂移方向
（控制台说准许、程序去取时被拒）。那份「如果它还能登录会是什么样」的清单降到
下面一行，仍然说得出来，但不冒充「现在」。
根治是让 `worker/visibility.ts` 的重算也看 `enabled`，那会牵到调度器那一侧，未做。

### 4.6 自动规则

### 4.8 定时任务

![定时任务](screens/11-定时任务.webp)

五个任务分两组显示。主链路是拉取 → 归档 → 自动授权三步：上一步有新产出时
下一步立刻接着跑（后端 `JOB_CHAINS`，控制台 `pages/Jobs/view.ts` 的 `CHAIN_AFTER`
抄同一份，`tests/store/jobs-chain-copy.test.ts` 钉住），到点也照常跑。清理到期文件
与刷新采集清单各按自己的周期独立运行，不接在别的任务后面。表里的序号是
`JOB_CATALOG` 的顺序，页面上只给链上的三步标步数：

| 任务 | 频率 | 干什么 |
| --- | --- | --- |
| 一、拉取新录制 | 每 15 分钟 | 从腾讯会议下载新录制到本地 |
| 二、归档到 NAS | 每小时整点 | 把本地文件写进 NAS 并校验哈希 |
| 三、清理到期文件 | 每天 03:00 | 删掉已过期且已归档的本地文件，记录保留 |
| 四、刷新采集清单 | 每 5 分钟 | 重算每个程序能取走哪些会议的哪些资产 |
| 五、自动授权 | 每 5 分钟 | 把规则放行的会议授权给开了自动授权的程序 |

> 「干什么」一列逐字就是 `src/store/jobs.ts` 里 `JOB_CATALOG[].what`，
> 界面上显示的也是它。`console/src/api/mock/jobs.ts`（原型模式）再抄一份。
> 三处曾经各写各的，原型那份比生产长一倍、任务四的频率还写成「每 30 分钟」，
> 于是所有原型截图和视觉验收量的都是一页并不存在的文字。
> `tests/store/jobs-copy.test.ts` 现在钉住这三处一致。
> 「每天 03:00」用的时区来自 `MDE_SCHEDULER_TZ_OFFSET_MIN`，调度器与控制台读同一个值。

- 每个任务带一条近期运行的 sparkline，失败的那次是红的
- 失败项不会静默丢弃，会一直留在下方的「失败项 · 需要处理」表里等重试，
  且明写影响（归档那条是「本地文件到期清理后，这场会议就一份都不剩了」，来自
  `JOB_CATALOG[].impact`）和已重试次数（`2 / 5`）。任务卡上那一行的标签是
  「影响：」，失败项表里那一列叫「如果不处理」，同一批字，两处问的问题不一样
- 失败项按「任务 + 原因 + 影响」归并显示：三段文字逐字相同的是一行，涉及的会议
  写成一个可展开的数字；组与展开的明细都分页，页面高度不随失败项数无限长。
  不做固定高度的框内滚动，页面已经在滚，框里再滚一层就是两条滚动条打架
- 失败项的原因是一句人话（「录像：腾讯那边没有这个文件」），原始报错在同一格里
  一个默认收起的「技术详情」折叠中。两者分列不是排版偏好：归并键就是那句原因，
  原始报错里带着 remote_id 与本地路径，留在原因里会让一轮拉取里 23 场同一件事的
  会议变成 23 行。翻译口径在 `src/worker/failure-text.ts`
- 拉取任务的失败项能单独处理：行上是「重试」「忽略」，归并组上是「全部重试」
  「全部忽略」。重试把那场会议的 failed/dead 资产打回下载队列并清零重试计数；
  忽略把 dead 判成「不用管了」（`skipped/ignored_by_admin`），下一轮不再登记。
  两个动作都要管理员写权限、都留审计。其余任务的失败项不给按钮，它们每轮
  由各自的枚举源重新判定、自动恢复，一颗点下去只会回一句「这条没能处理」的按钮
  比没有按钮更糟
- 页顶两条横幅各说一件事，两条都能关，关的都只是「眼前这一段」。
  「N 个任务已经落后」意味着调度器多半不在跑了，关掉的是这一批落后（身份 =
  落后任务按名字排序后拼成的 `<name>@<lastRunId>`，存 `mde.jobs.overdue.dismissed`），
  任一落后任务再跑一轮、或落后集合变了，它就回来。
  「最近 N 轮拉取连续失败」写观察、能做什么、超过拉取窗口要人工补拉，关掉的是
  这一段故障（身份 = 最新那次 failed 运行的 id），又失败一轮就回来。
  后者只在这一页显示，不进顶栏的全局状态条，理由见 §7.1

## 5. 规则引擎语义

这一节需要逐字实现，不能凭直觉。实现在 `src/policy/stacks.ts`。

### 5.1 求值

```
对某一类规则（fetch / archive / allow）：
  1. 取出该类中 enabled 的全部规则
  2. 按 priority 降序排序
  3. 从上往下找第一条匹配的，用它的 effect，立即停止
  4. 一条都不匹配时用兜底：allow 类 → deny，其余 → skip
```

第一条命中的说了算，不做合并、不做叠加。

三条必须写死的细节：

1. 同优先级的平局按 `id` 升序，先建的先命中。 不按 effect 决定平局：
   「deny 优先」是另一套语义（合并式），与本节的「第一条说了算」互斥，混用会让
   规则列表的顺序不再是判定顺序，管理员就读不出结果了。排序只有 `sortStackRules`
   一份实现，规则列表读的也是它。
2. 命中的规则 effect 是脏数据时不继续往下找。 往下找会让一条写坏的高优先级
   deny 被低优先级的 allow 顶掉，那是查不出来的静默放行。正确处理是「这条规则说了算，
   但它说不清楚」，落到本栈的安全侧（fetch/archive → skip，allow → deny），
   `source` 记 `'rule_invalid'`。规则没命中但原因是这场会议缺了它要用的事实
   （`conds.ts` 的 `fact_missing`）时同理，也不往下找。
3. fetch / archive 两栈显式忽略主体。 `policy_rules.subject_type` 是 `NOT NULL`，
   库里存在带主体的历史行，若按「主体不符就筛掉」处理，这些规则会整条消失。
   忽略这件事要在 trace 与静态检查里说出来，否则脏数据在界面上是隐形的。

旧的单栈实现 `src/policy/engine.ts`（按 priority 升序取第一条、同优先级 deny 优先）
已经删除，三栈实现是唯一的判定路径，网关与调度器都走它。

### 5.2 单条规则的匹配

```
无条件（conds 为空）           → 匹配一切
join === 'or'                  → 任一条件成立即匹配
join === 'and'（默认）         → 全部条件成立才匹配
```

一条规则内只有一个连接词，不支持括号与混用。

### 5.3 可用字段与运算符

| 字段 | 运算符 | 值 |
| --- | --- | --- |
| 会议标题 `title` | 包含任一 / 不包含 | 关键词，逗号分隔 |
| 主持人部门 `dept` | 属于 / 不属于 | 部门多选 |
| 主持人 `host` | 是 / 不是 | 人员 |
| 会议时长 `dur` | 大于 / 小于 | 分钟 |
| 录制结束 `age` | 在最近 N 天内 / 早于 N 天 | 天 |
| 归档状态 `arch` | 已写入 NAS / 未归档 | 无值 |

> `dept` 依赖企微通讯录，网关没有这份数据。 它是归档规则最自然的写法
> （「财务部的会议归到 /nas/meetings-finance/」），所以不删这个字段。当初的计划是
> 把「接企微通讯录 API + 部门同步」立成阶段 3 的前置任务 R0。
>
> R0 已定为不做（2026-08-25）。 接通讯录 API 的前提是有企业微信自建应用，
> 而这个应用没有真建：`WECOM_CORP_ID` / `WECOM_AGENT_ID` / `WECOM_SECRET` 三项
> 要么全填要么全不填（`src/config.ts`），全不填是合法形态，此时四条设备授权路由
> 返回 501 `wecom_not_configured`。M3.5 的部署决策本就是不建自建应用
> （`docs/history/m3.5-execution-plan.md` §2 决策 2）。所以降级路径是当前的最终形态：
> 字段可见、禁用、写明原因。引擎里对 `dept` 条件显式判不匹配（`conds.ts` 的
> `evalDept` 走 `no_data_source` 分支），且与「字段拼错」分开，判定理由说得出
> 「这个字段当前无数据源」。一条只有 `dept` 条件的规则永远不会命中，规则列表要给出
> 可见提示。将来真建了企微应用，R0 立刻回来。

### 5.4 人工改写

单场会议的人工改写优先于所有规则。改写过的会议在列表里有标记，
且规则的影响预览要把它们排除在「会被改变」之外。改写替换的是规则判定结果，
授权是另一个独立的「与」，两者管的不是同一件事（见 §1.3 与 §4.5）。

### 5.5 影响预览的计算范围

只在 `命中(旧规则) ∪ 命中(新规则)` 这个集合上算，不是全部会议。
把所有会议都列成「受影响」是虚假的规模感。

## 6. 数据模型

### 6.1 会议

```js
{
  id, title, code,            // 会议号 881-123-40
  when, host, dur,            // 8-21 14:00 · 邹研发 · 1:52
  assets, total,              // 已拿到 / 应有
  fetch:   'done' | 'running' | 'blocked' | 'none' | 'off',
  archive: 'done' | 'running' | 'failed' | 'off' | 'blocked' | 'none',
  // 'off' = 被人工关掉（圆点即开关，见原型 toggleStage）。它既不是 blocked
  //         （规则拒绝），也不是 none（没东西可做）。两个阶段都有这个取值。
  // 'none' = 压根没有录制，无从决定。
  // 这两个取值原本都漏在本表外，因为种子数据里没有、只在运行时产生：
  //   ArchiveState 的 'none' 由 F1 Task 2 发现，FetchState 的 'off' 由 F1 Task 6 发现。
  allow:   'allow' | 'deny',
  grants:  ['知识库索引器', ...],   // 只有 allow 且在保留期内才有意义
  hand:    [],                      // 被人工改写过的阶段
  keep: { archivedOn, expiresOn, daysLeft, extended, filesGone },
  nas, size,
  why: { fetch: {by, text}, archive: {...}, allow: {...} },  // 逐阶段判定理由
  hist: [[时间, 事件], ...]
}
```

`why.by` 的取值决定理由的呈现样式：`rule`（来自规则）· `hand`（人工改写，琥珀）·
`fail`（失败，红）· `expired` / `wait` / `na`（生命周期原因，优先级高于权限原因）。

### 6.2 五类资产

| `AssetKey` | 名称 | 网关 `asset_type` | 来源 |
| --- | --- | --- | --- |
| `video` | 录像 | `video` | `/v1/addresses` |
| `audio` | 音频 | `audio` | `/v1/addresses` |
| `transcript` | 逐字稿 | `meeting_summary` | `/v1/addresses` |
| `ai_minutes` | 纪要 | `ai_minutes` | `/v1/smart/minutes` 默认模板 |
| `chapters` | 时间轴 | `chapters` | `/v1/smart/chapters` |

这一列的权威在代码里，不在本表：`packages/engine/src/domain/types.ts` 的
`ASSET_KEY_TO_GATEWAY_TYPE` 是唯一事实源，本表只是它的人类可读副本。两处不一致时以代码为准。

「应有」这个数按录制类型裁剪，不是恒为 5：

- 转写记录（`/v1/corp/records` 的 `record_type = 3`，平台给主题加前缀「转写_」）
  只有逐字稿与纪要两类。`/v1/addresses` 照样给出 mp4 链接，但对象存储对它一律
  404，音频与章节从未出现过。迁移 016 起 `record_type` 落库，发现层按它裁剪，
  这类会议不再卡在「差一个」
- 普通云录制从不产出 audio。video 就绪而 audio 缺席直接判 `not_generated`，
  不进探测表空等
- 没开智能录制的会议没有章节，探测到期后判未生成，时间轴 tab 为空并说明原因

原型 HTML 内部那套短名（`summary` / `aitr` / `digest`）一个字都不许进代码：
前后端一律用左列的 `AssetKey`。同一批资产已经有过三套叫法，M3.5 为此吃过一次亏
（见 `dev-plan.md` §5 C7）。中文名的唯一事实源是 `src/domain/asset-labels.ts`。

同一份录制的多种导出格式（txt / docx / pdf）共享同一个 `record_file_id`，
只有 `file_type` 能区分它们。这个坑已经在 `client/src/store/db.ts` 的 schema v2
里踩过并修了，控制台侧的资产计数沿用同样的唯一键。

### 6.3 规则

```js
{ id, kind: 'fetch'|'archive'|'allow', pri, enabled,
  join: 'and'|'or', conds: [{ f, op, v }], effect,
  note,          // 说明，会出现在规则列表和每场会议的判定理由里
  author, on }   // 谁在什么时候建的
```

主体（谁）在三栈里的含义不同：

| 栈 | 主体 | 说明 |
| --- | --- | --- |
| 拉取 `fetch` | 无 | 系统级行为，不针对任何人 |
| 归档 `archive` | 无 | 同上 |
| 采集权限 `allow` | 采集程序 | 不针对人。对应 `service_accounts.id` |

`policy_rules.subject_type` 的 `program` 取值由迁移 004 加入；fetch / archive
两栈的主体列留空，并在引擎里显式忽略（见 §5.1 第 3 条）。

### 6.4 采集程序

```js
{ id, name, scope }   // kb-indexer · 知识库索引器 · '纪要 + 逐字稿'
```

## 7. 系统状态与降级

控制台依赖三个外部系统，它们各自挂掉的后果不同，所以告警等级和给出的
操作也不一样。

| 依赖 | 挂了会怎样 | 等级 |
| --- | --- | --- |
| 腾讯会议接口 | 只影响拉新的。已拉下来的会议、归档、对外采集都不受影响 | 琥珀 |
| NAS 归档存储 | 归档不成功的会议，本地保留期一到就彻底没有了，这是本系统唯一不可逆的损失 | 红 |
| 数据库 | 整个后台读不出数据，但不会丢东西，文件还在，记录还在 | 红 |

### 7.1 腾讯会议不可达

![腾讯会议不可达](screens/15-系统状态-腾讯会议不可达.webp)

> 截图里顶栏那条琥珀横幅已经不在了（2026-09-03 定），下面写的是现状。

后端没有探测腾讯会议连通性的端点，有的只是「拉取新录制」最近几轮都失败了这个观察
（`fetch_recordings` 的 `recentRuns` 从最近一次往回连着 `failed` ≥ 3 轮，
`countConsecutiveFailures()`）。所以界面上只说观察（「最近 N 轮拉取连续失败」），
不说结论（「腾讯会议不可达」），后者是在替一个我们没有的探测下结论。

这一条不进全局状态条。全局状态条留给「此刻有一个能阻止损失的动作」的事：
NAS 断连给「暂停到期清理」（§7.2），系统状态读不到给「重试」。拉取连续失败没有这样的动作：

- 调度器每 15 分钟自动再试一轮，「立即运行」只是再排一轮同样的事
- 失败原因就三类：接口返回的结构变了（要改代码）、凭证或网络不通（在控制台之外处理）、
  录制在腾讯侧已经过期或不存在（谁也做不了什么）
- 唯一需要人出手的情形是连续失败超过拉取窗口（`MDE_SCHEDULER_FETCH_LOOKBACK_HOURS`，
  默认 24 小时）。调度器每轮只回看这一段，中断更久的话，中间的会议不会被回头补上，
  修好后要用 worker 命令行按时间段或会议号补拉。控制台没有这个入口

一条挂在每一页上的横幅是在说「现在就动手」，而这件事诚实的版本是「等着，看一眼原因，
超过一天记得补拉」。所以它只在三处可见：

| 出口 | 说什么 |
| --- | --- |
| 左栏底部摘要 | 「拉取可能不通 · 最近 N 轮拉取连续失败」 |
| 左栏「定时任务」旁的红点 | 有你还没看过的新失败（§3） |
| 定时任务页顶部的横幅 | 观察、能做什么、超过窗口要补拉。可关闭，按这一段故障里最新一次失败运行的 id 记，又失败一轮就回来，拉通一次就忘掉 |

拉取窗口的小时数由 `GET /api/v1/admin/jobs` 的 `fetchLookbackHours` 下发：网关与调度器读的
是同一个环境变量，定义只有 `src/store/jobs.ts` 一份，控制台不自己写 24。

### 7.2 NAS 断连

![NAS 断连](screens/14-系统状态-NAS断连.webp)

故障必须在数据里可见，不能只是一条横幅。NAS 断连时：

- 分诊条的「归档失败」从 1 变成 5
- 受影响会议的保留窗口被清零（它们本来就不该开始计时）
- 它们的授权被撤下（没归档成功的东西不该对外可见）
- 告警条上直接给「暂停到期清理」，这是唯一能阻止不可逆损失的动作，
  所以它在告警条本身上

## 10. 明确不做（YAGNI）

- **AI 问答**（把会议内容送给模型）：见 §1.4。写了条件，没有实现；界面上也不
  留位置（2026-08-28 起，内容预览页不再渲染那块说明）
- **企微扫码登录控制台**：控制台走独立的账号密码体系（D1，2026-08-23）。
  它是 1-3 人的运维面板，要在 NAS 断连、企微不可达这类故障时能登录，所以登录不能依赖
  另一个可能同时挂掉的系统。这条是明确不做，不是暂缓
- **多租户 / 多企业**：单企业部署
- **自助注册 / 找回密码**：管理员由系统管理员开通
- **移动端完整体验**：移动端只保证「能看」，不保证「能改」，见 §11
- **新建定时任务**：§4.8 的五个任务是 `src/store/jobs.ts` 里 `JOB_CATALOG` 的五个
  常量，不是一张表。要开放自定义任务，先得回答「执行体从哪来」，那是一个新子系统，要解决沙箱、依赖、失败语义、权限四件事，远不止一个表单。而这五个任务已经串起了整条链路
  （拉取 → 归档 → 清理 → 刷新采集清单 → 自动授权），没有第六件事非做不可。原型里那个「新建任务」
  按钮点了只弹一句「还没做」，F5a 已经把它删掉：按钮在承诺一个不存在的功能（阶段 5 计划裁定 G-g，2026-08-26）
