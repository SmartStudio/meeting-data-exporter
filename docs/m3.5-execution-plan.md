### 为什么不换 SQLite

网关对 MySQL 的耦合面（实测计数）：

```
直接 import mysql2 的文件      13 个（5 个 store 模块 + preflight + 7 个测试）
RowDataPacket / Pool 类型标注  32 处
MySQL 方言 SQL                 17 处
  ON DUPLICATE KEY UPDATE · JSON 列类型 · UNIX_TIMESTAMP() ·
  AUTO_INCREMENT · ENGINE=InnoDB · TINYINT(1)
migrations/001_init.sql        8 张表，全 MySQL 语法
```

`mysql2` 的类型直接出现在 store 模块的**公开签名**里，没有持久层接口——
换 SQLite 不是「换实现」而是「重写持久层 + 迁移 + 全部 DB 测试」，并且从此
长期维护两套方言（投产仍是 MySQL）。Docker MySQL 是一条命令、零代码改动、
且与投产同构。

> 对照：客户端 `client/` 的 `storage` 从第一天就是接口，所以 M4 加 OSS 只需
> 新增实现类。同一仓库一边可换一边不可换，差别只在当初有没有在边界留接口。

## 3. 目标架构

```
                     ┌── 腾讯会议 ──GET/POST──> 43.156.203.171:9999 ──┐
                     │   （webhook：内容自带 AES 加密 + sha1 验签，       │
                     │     腾讯官方允许 HTTP，故传输层不加密可接受）      │
                     │                                                  ↓
阿里云 RDS <─────────┼────────────────────────────────────  网关（bun 直跑）
meeting_db 8.0.36    │                                       HOST=0.0.0.0 PORT=9999
（白名单放行 VPS）    │                                                  │
                     │                                        调腾讯 REST API
                     │                                                  ↓
Mac: mde CLI ──SSH 隧道──> 127.0.0.1:9999 ──> 网关 ──签发临时地址──> 客户端直连
     （凭证走加密隧道，不明文过公网）                             腾讯对象存储下载
                                                                  ↓ 文件落 Mac
```

**不碰 Caddy、不碰 new-api、不改任何现有配置文件。** 生产栈零风险。

### 两条流量的安全模型不同

| 流量 | 机密性由谁保证 | 结论 |
| --- | --- | --- |
| 腾讯 → 网关（webhook） | **应用层**：AES-256-CBC 密文 + sha1 验签 | HTTP 可接受（腾讯官方自己也允许） |
| mde CLI → 网关 | **传输层**：client_secret / access_token 是裸凭证 | 必须走 SSH 隧道 |

同一个端口，两种要求，措施可以不同。这不是将就。

### 为什么用 bun 直跑而不是 Docker 镜像

webhook 格式我们只核实过文档、没实测过，大概率要改几轮。裸进程改完重启 2 秒，
Docker 要重建镜像。**联调通过后再切 Docker 镜像**（`Dockerfile` 已有）。

## 4. A · 代码改动（我做）

### A1 · webhook 对齐官方契约 【必做】

不改的话，你在腾讯后台点「保存事件订阅」会**直接失败**（没有 GET 验证端点）。

| 落点 | 改动 |
| --- | --- |
| `src/http/handlers/webhook.ts` | POST：`timestamp`/`nonce`/`signature` 改从 **Header** 读（原从 query）；密文字段 `encrypt` → **`data`**；成功响应改为**纯文本** `successfully received callback`（不能带引号/换行，原为 `{"ok":true}`） |
| 同上（新增） | `handleWebhookVerify`（GET）：urldecode `check_str` → 验签（token/timestamp/nonce/**check_str**）→ 解密 → **3 秒内返回纯文本明文** |
| `src/http/router.ts:88` | 注册 `GET /webhook/tencent-meeting` |
| `src/sts/crypto.ts:66` | `decryptEvent` 去掉企微的 `16 随机字节 + 4 字节长度头` 结构，改为官方的 **`msg + $key`**：PKCS#7 去填充后取 JSON 前缀（`$key` 是 base64 字符集、不含 `}`，按最后一个 `}` 截断安全） |
| 同上（防御） | 官方签名文档的样例里 `data` 解 base64 后**直接是明文 JSON**（未加密）。故：先尝试 AES 解密；失败则检查 base64 原文是否本身就是合法 JSON，是则走该路径并记一条 warn。**验签在前且强制**，所以这个回退不削弱安全性 |
| `tests/http/webhook.test.ts` | 用官方样例做回归：`token=bVPU6F8Htxl5XkAbp3jGV2xWp` / `timestamp=1609239040864` / `nonce=14964161` / 官方 `data` → 签名必须等于 `b11e507817336a91d7df0c8536ee2aca18bbbae8` |

**明确不改**（已核实与官方逐字吻合）：签名算法（字典序拼接 + sha1）、
`AESKey = Base64_Decode(EncodingAESKey + "=")`、IV 取 key 前 16 字节、
AES-256-CBC、PKCS#7、事件名 `common.sts-token`、
`payload[0].token_info.{req_id, sts_token, expire_ts}`、
`POST /v1/app/sts-token` 的 `operator_id`/`operator_id_type=1`/`valid_time=24`。

**一个已知未知**：GET 验证解密出的明文是否也带尾部 `$key`，官方未写明。
按文档原样返回，并在验签通过后打日志；若后台保存失败，看日志再决定是否剥离。

### A2 · 配置空串缺陷 【必做】

`src/config.ts`：新增「空串视同缺失」的读取器用于 `TM_QPS` / `TM_BASE_URL`；
`qps` 加 `>= 1` 的启动期校验（照抄现有 `TRUSTED_PROXY_HOPS` 的写法）。
同步修正 `.env.example` 里「留空则使用默认值」这句**与代码不符**的注释。

### A3 · 企微降级为一等公民的「未配置」 【做】

`WECOM_*` 缺失时 `loadConfig` 不再报错；`/api/v1/auth/device/code`、
`/api/v1/auth/device/token`、`/device`、`/auth/wecom/callback` 返回
`501 wecom_not_configured`；preflight 第 5 项判 **skip 而非 fail**。

理由：占位符的本质是**让代码相信一个假事实**，再靠人记住它是假的。人记不住——
三周后没人知道那一项红是「已知可接受」还是「刚坏的」。一个永远红的检查，
和一个坏掉的检查，在实践中是同一件事。

### A4 · `Bun.serve` 支持 HOST 绑定 【小】

`src/index.ts`：`hostname: process.env.HOST ?? '0.0.0.0'`。

### A5 · `scripts/seed-dev.ts` 【做】

读 `.env` → 生成随机 secret → 建策略规则（`subject_value` = `TM_OPERATOR_ID`）
+ 服务账号（`tm_userid` 同值）→ **只打印一次凭证、不落盘**。幂等可重跑。

替代两段容易写错的手工 SQL：列名是 `subject_value` 不是 `subject_id`、
两处 userid 必须一致（不一致的表现是「资产列表返回空数组」，与「这场会真没录制」
无法区分）、argon2 hash 要手工搬运。

**每项验收**：`bun test`（根目录，需 `TEST_DATABASE_URL`）+ `cd client && bun test`
+ 两侧 `tsc --noEmit` 全绿。

## 附 · 已核实的腾讯官方契约（备查）

来源：腾讯云文档 1095 系列 —— 51608《回调服务要求》、51612《签名校验》、
54658《事件加解密》、127650《企业自建应用票据》、127651《STS Token 生成》、
42413《企业自建应用鉴权（AKSK）》。核实日期 2026-08-21。

### 鉴权 Header

| Header | 含义 | 我们的 env |
| --- | --- | --- |
| `AppId` | 腾讯会议分配给企业的**企业 ID** | `TM_APP_ID` |
| `SdkId` | **应用 ID**（存在则必填） | `TM_SDK_ID` |
| `X-TC-Key` | SecretId | `TM_SECRET_ID` |
| `X-TC-Registered` | 固定 `1` | — |

> 后台「应用凭证」页显示为「企业ID / 应用ID」，与文档的 AppId / SdkId 是同一
> 组东西的两种叫法。填反会得到 `190303`。

### 回调 · GET（URL 有效性验证）

```
GET <你的URL>?check_str=<加密后 base64，需 urldecode>
Header: timestamp / nonce / signature
```

处理：验签（token/timestamp/nonce/**check_str**）→ base64 解码 → 解密 →
**3 秒内返回明文字符串**，不能加引号、换行，否则后台保存失败。

### 回调 · POST（事件推送）

```
POST <你的URL>        Content-Type: application/json
Header: timestamp / nonce / signature
Body:   {"data":"<加密后 base64>"}
```

处理：验签 → 解密 → **返回 HTTP 200 且响应体为纯文本
`successfully received callback`**。其他一律视为失败，腾讯会在
**1 / 3 / 6 分钟**后各重试一次，共三次。5 秒无响应即断开。

### 签名算法

```
signature = sha1( 将 token、timestamp、nonce、data 四个值按字典序排序后拼接 )
```

官方样例（已实算验证）：

```
token     = bVPU6F8Htxl5XkAbp3jGV2xWp      （恰好 25 字符）
timestamp = 1609239040864
nonce     = 14964161
data      = eyJldmVudCI6Im1lZXRpbmcuY3JlYXRlZCI...
→ signature = b11e507817336a91d7df0c8536ee2aca18bbbae8   ✅ 与我们的实现一致
```

### 加解密

```
AESKey = Base64_Decode(EncodingAESKey + "=")     → 32 字节
算法   = AES-256-CBC，PKCS#7 填充
IV     = AESKey 的前 16 字节
明文   = msg + $key                （msg 为 JSON；⚠️ 与企微的 16+4 字节头结构不同）
EncodingAESKey = 43 字符，取自 a-z A-Z 0-9 共 62 字符
```

### STS-Token

```
接口：POST https://api.meeting.qq.com/v1/app/sts-token
入参：operator_id / operator_id_type=1 / valid_time（枚举 6、12、24）
出参：{ "req_id": "..." }
权限：自建应用需「管理企业资源」；操作者需超级管理员或管理员
事件名：common.sts-token
回调 payload[0]：operator.userid、token_info.{req_id, sts_token, expire_ts}
```

**依赖边界**：只有《查询录制转写详情》和《查询单个录制详情》两个接口强制要求
Header 携带 STS-Token。对应到我们的资产类型——

| 资产 | 来源 | 需要 STS |
| --- | --- | --- |
| `video` / `audio` / `transcript` | `/v1/addresses`（批量） | **否** |
| 全部 `ai_*`（含默认集里的 `ai_transcript`） | `detailByFileId`（详情） | **是** |

STS 不可用时 catalog **静默跳过** ai_*（字段缺失即不产生该资产），
`listAssets` 不报错、只是少几项——**这不是客户端 bug**。
