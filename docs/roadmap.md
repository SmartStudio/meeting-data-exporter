| 项 | 内容 | 落点文件 | 与谁冲突 |

### 执行编排

```
波次 1（并行 3）   B1 · B3 · B4        文件互不重叠，可同时派
波次 2（串行 1）   B2 + B5             都碰 index.ts，合并给一个 agent 顺序做
波次 3（单独）     B6                  需先决策归属，见下
```

B2 与 B5 落在 `index.ts` 的不同区域（密钥装配 vs 续期循环），但同一文件不宜并行——合并成一个「index.ts 装配加固」任务，一个 agent 顺序完成两件事最干净。

### B6 归属决策（已定并实现）

企微扫码登录的完整修复需要一个 `/device` 验证页面（浏览器访问，用户在此确认授权）。当时两个选择：

- **网关提供最小 /device 页面**（推荐）：设备授权流程是网关的对外契约，页面理应由网关兜底。
- **划归桌面端/前端**（子项目 4）：若登录只在桌面应用内发生，可由桌面壳内嵌 webview 承接。

**决策：采用前者。** 已实现 `GET /device`（`src/http/handlers/device.ts`）——凭 `user_code` 反查 `state` 后 302 跳转企微扫码登录页，让「仅凭网关就能走完真人登录」成立（US-2.1 前提）。桌面端将来仍可用内嵌 webview 覆盖更好的体验。

### 规模

B1–B5 都是小到中等改动（各自 1–3 个文件、逻辑明确），适合一轮并行执行清完。B6 稍大且需决策。整体约 **2 波并行 + 1 个决策项**。

## M3.5 · 真实环境联调（当前下一步）

**为什么单列一块**：`client/` 至今只对「我们自己写的假网关」验证过，而假网关是照着
`client/src/gateway/client.ts` 的期望写的——两者必然吻合，**不构成对真实网关的证据**。
这是整条链路上唯一未被真实验证的环节，也是投产前的实际门槛。

需要在同一个联调环境里一起做的三件事：

| 事项 | 来源 | 说明 |
| --- | --- | --- |
| 核实资产字段名 | spec §17 已知未知 | `listAssets` 响应里 `remote_id`/`state`/`allow_download`/`file_type`/`bytes_expected` 目前按网关 §5.2 契约**推断**，需拿真实响应校验 |
| `preflight --sample-user` 实测 | M2 遗留 Q1 | 确认企微 userid 与腾讯会议企业 userid 是否逐字节一致；不一致则把 `IDENTITY_STRATEGY` 切 `table`（仅改配置） |
| webhook 线路格式核实 | deploy.md §11 | STS 回调的签名/加解密格式系仿企微自行设计，须对照腾讯官方文档核实 |

**接缝已留好**：字段映射集中在 `gateway/client.ts` 一个函数里，真实字段名不同只改那一处，
不影响下游；`assetId` 全程当**不透明串**传递、不解析格式，天然免疫格式差异。

**下一步 M3.5（真实环境联调）**：网关与客户端都已实现完整、各自测试全绿，但两端至今只在
「自己写的替身」之间验证过。M3.5 把三件必须在真实环境做的事一次做完（见上文表格），
它既是投产门槛，也会一次性消掉 spec §17 的全部「已知未知」。

**为什么这件事不能省**：本项目已经吃过两次「替身比真实依赖宽容」的亏——子项目 1 的设备登录
26 个测试全绿却在真实 MySQL 下完全不可用；M3 的 `openDb` 42 个测试全绿却在真实文件路径下
必崩（单测全用 `:memory:`）。两次都是替身宽容掩盖了真实约束。假网关同理。

**联调之后**：M4（存储扩展）与 M5（桌面端）可并行——`storage` 从第一天就是接口，M4 只新增
实现类、`executor` 不改；M5 直接读 M3 的同一 SQLite 展示进度。
