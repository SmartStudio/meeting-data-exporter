## M1 · 网关加固（让网关可上线）

清掉最终整体审查判定的 6 项「上线前必须修」。目标是把「代码完成」推进到「可投产」。

### 落点与冲突分析

| 项 | 内容 | 落点文件 | 与谁冲突 |
| --- | --- | --- | --- |
| **B1** | 登录端点限流 + 服务账号恒定时间比较（消除枚举预言机） | 新增限流中间件 · `auth/service.ts` · `http/router.ts` | 独立 |
| **B2** | STS 加密密钥与 JWT_SECRET 分离 + JWT_SECRET 强度校验 | `config.ts` · `index.ts`(密钥装配区) · `.env.example` | **与 B5 争 index.ts** |
| **B3** | 策略引擎 NaN 静默放行 → 加载期校验 + NaN 视为不匹配 | `policy/expr.ts` | 独立 |
| **B4** | 腾讯错误分类在 HTTP 层映射（不再全塌 500） | `http/handlers/meetings.ts` · `http/respond.ts` | 独立 |
| **B5** | STS 看门狗接线：调度 expireStale + ensureFresh 去重在途 pending | `index.ts`(续期循环区) · `sts/manager.ts` · `store/sts.ts` | **与 B2 争 index.ts** |
| **B6** | 企微扫码登录接通（verification_uri 指向的 /device 缺失） | 见下方「需先决策」 | 独立但最大 |

### 执行编排

```
波次 1（并行 3）   B1 · B3 · B4        文件互不重叠，可同时派
波次 2（串行 1）   B2 + B5             都碰 index.ts，合并给一个 agent 顺序做
波次 3（单独）     B6                  需先决策归属，见下
```

B2 与 B5 落在 `index.ts` 的不同区域（密钥装配 vs 续期循环），但同一文件不宜并行——合并成一个「index.ts 装配加固」任务，一个 agent 顺序完成两件事最干净。

### B6 需先决策

企微扫码登录的完整修复需要一个 `/device` 验证页面（浏览器访问，用户在此确认授权）。这块归属未定，两个选择：

- **网关提供最小 /device 页面**（推荐）：设备授权流程是网关的对外契约，页面理应由网关兜底。成本：一个服务端渲染的最小 HTML 端点
- **划归桌面端/前端**（子项目 4）：若登录只在桌面应用内发生，可由桌面壳内嵌 webview 承接

建议先按前者做一个最小可用页面，让「仅凭网关就能走完真人登录」成立（US-2.1 的前提），桌面端将来可以覆盖更好的体验。

### 规模

B1–B5 都是小到中等改动（各自 1–3 个文件、逻辑明确），适合一轮并行执行清完。B6 稍大且需决策。整体约 **2 波并行 + 1 个决策项**。

## M2 · 业务确认（✅ 已完成，2026-07-21）

两个问题均已由项目方确认，且与代码当前的安全默认值一致——无需改核心代码。

| 问题 | 确认结果 | 影响 |
| --- | --- | --- |
| **Q1** 账号体系？ | 企微账号、无独立体系、无 SSO → 身份映射选 **`direct`** | 仅剩一个动作：`preflight --sample-user` 实测两侧 userid 是否逐字节一致，不一致切 `table` |
| **Q2** 谁能导出？ | **仅管理员** | 当前最小模板即最终形态；**M5 桌面端定位为管理员工具**（非全员传播型） |

**M2 唯一遗留动作**：Q1 的 preflight 实测，须在有真实企微凭证的环境执行——归入 M1 的部署自检环节或子项目 2 联调时一并做。

**对下游的确定性影响**：M5 桌面端从「全员传播型产品」正式改为「管理员工具」，用户故事与 spec 已同步。这消除了立项时的一处定位模糊——桌面端将来只需服务几人到几十人的管理员群体。

## M3 · 子项目 2：核心导出引擎 / 客户端 CLI

让整个工具真正能用的一块。设计已在 spec 附录 A（数据库即任务队列、断点续传、资产粒度去重、最小 CLI）。

- **前置**：M1 完成（客户端依赖网关的对客户端 API，契约已定）
- **核心难点**：大文件断点续传（5 分钟链接时效下的换链续传）、SQLite 任务状态机、幂等去重
- **交付**：能把指定时间范围或指定会议的四类资产完整拉到本地，可断点续跑的 CLI
- **形态**：Bun + TypeScript + `bun:sqlite`（客户端侧用 SQLite，与网关的 MySQL 分开）

这一块可以像子项目 1 一样走完整流程：spec → 用户故事对照 → writing-plans → 并行执行。

## 推荐路径

```
Q1/Q2 已确认 ✅（M2 完成，仅剩 Q1 的 preflight 实测待联调环境）
现在  ──→  M1 波次 1（B1/B3/B4 并行） ──→ M1 波次 2（B2+B5） ──→ 决策 B6 归属
                                                    │
                              M1 清完  ──→  网关可投产  ──→  启动 M3（子项目 2）
                                                                    │
                                                              M3 完成 ──→ M4 / M5 并行
```

**为什么先做 M1 而不是直接上 M3**：M1 的 6 项里有 4 项是安全或数据正确性（限流、密钥分离、NaN 放行、错误分类），趁子项目 1 的上下文还热、执行台账还在，一轮并行能清得干净；等做完 M3 再回头,重建上下文的成本会高得多。而且 M3 的客户端要连网关联调，网关先加固到可投产，联调才踩得实。

**一个例外**：如果目标是尽快看到「端到端能导出一场会议」的可演示效果，而非先上生产，那可以先做 M3 的最小闭环（跳过 B1/B2 这类纯安全加固），用本地单实例网关联调——但这条路要明确「不能上生产」，且 M1 的债迟早要还。
