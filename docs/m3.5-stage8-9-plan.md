## 0. 为什么这五项不能继续欠着

它们是本项目设计里最值钱的五个机制，而**服务端的归档 worker 现在就在持续跑它们**：

| 机制 | 设计文档 | 没验证的后果 |
| --- | --- | --- |
| 完整闭环 | 引擎 spec §12 | 不知道端到端真能跑通 |
| 幂等（重复跑不重下） | 引擎 spec §6 | 归档 worker 每轮重下全部资产，NAS 与带宽双倍消耗 |
| **断点续传** | 引擎 spec §10 | **全靠对象存储支持 Range，这一条至今没有真实证据**。不支持的话几个 GB 的录制中断就得从头来 |
| 崩溃恢复（租约过期重领） | 引擎 spec §6 | 任务永久卡在 `running`，归档静默停滞 |
| AI 纪要延迟探测 | 引擎 spec §9 | 刚结束的会议永远拿不到 AI 纪要，或反过来被判失败 |

本项目已经吃过三次「替身比真实依赖宽容」的亏（设备登录 26 测试全绿却在真实 MySQL 下不可用 ·
`openDb` 42 测试全绿却在真实文件路径下必崩 · `asset_type` 词汇表推断错误伪装成「视频没产出」）。
这五项目前的证据强度与那三次出事前**完全相同**。

### 跑出来的五个新事实

> **处置状态（2026-08-27 补记）：四条缺陷已全部修完，第 3 条经判断不改。**
> 逐条见下面每条末尾的箭头。这一节从此是「已结清」的记录，不是待办清单。

1. **Ctrl-C 之后立刻重跑，十五分钟内什么都不会发生，而且没有任何提示。**
   任务卡在 `running`，租约要到 claim + 900 秒才过期，`execute` 只会打印
   `completed=0 failed=0 skipped=0`。这是租约机制**正常工作**的表现，
   但对着这个输出的人不可能知道。**这是本次最值得修的一个体验缺陷。**
   → **已修（`27fa802`）**：一轮颗粒无收时现在会说清楚是「没活干」还是「活被租约锁着」。
2. **`_manifest.json` 的 `bytes` 字段实际恒为 null。** 当初刻意从 `bytes_written`
   改成 `bytes_expected`（前者是每 8MB 一次的进度检查点，当文件大小是假数据），
   但腾讯对这批资产**根本不返回 `bytes_expected`**，于是这个字段在真实环境里
   不携带任何信息。
   → **已修（`91d8840`）**：`downloadAsset` 完成那一刻的真实累加字节数（已过尺寸校验）
   经 `markCompleted` 落进 `bytes_written`，清单改取 `bytes_expected ?? bytes_written`，
   SQLite 与 MySQL 两个 Store、本地与 NAS 两份清单一起改。**本次改动之前就已完成的旧行**
   的 `bytes_written` 仍是默认值 0，那种说不清的 0 一律写 null，不写「0 字节」这个谎。
   连带修掉一条到期的竞态（`d9f487f`）：`touchProgress` 不 await，一次慢 UPDATE 能落在
   `markCompleted` 之后把真实大小盖回 8MB 检查点——两个宿主都加了 `AND status='running'`。
   **顺带的收益**：Stage 8 那条原判据（「视频字节数与 `bytes_expected` 一致」，已因该字段
   不返回而作废）现在可以直接从 `_manifest.json` 机器核对 `Content-Range` 总长，不必再跑一遍下载。
3. **目录名里的时间是 UTC。** 08-12 16:26（本地）的会议落进
   `2026-08-12_0826_…`。不是错，但看目录找会议的人会对不上。
   → **判断为不改（2026-08-27）**。目录名是幂等的锚：`meetingDirPath` 同时决定资产落盘路径
   与 sidecar 位置，换算成本地时区会让**已归档目录与新目录分叉**——NAS 上长出两套目录、
   幂等失效、同一场会议被重下一遍。代价远大于「看目录能对上时间」。正确做法是把
   「目录名时间为 UTC」写明（`packages/engine/src/domain/filename.ts` 的注释已经写了），
   要找会议按会议号找。**要改的话必须连带设计一次迁移，不能只改函数。**
4. **sidecar 每一轮都会重写**（带 `generatedAt`）。资产没重下，但两个 JSON 的
   哈希每轮都变——同步到 NAS 时会每轮重传。
   → **已修（`cda3088`）**：写之前先 `readMeta` 读回已有文件，除 `generatedAt` 外一字不差
   就不写，返回 `'unchanged'`。`Storage` 补了 `readMeta`（local / nas 都实现，NAS 版带超时），
   读不到一律当「要写」处理。NAS 那份的写入守卫（`fullyArchived && newlyArchived > 0`）原样没动。
5. **部署的服务端只有网关。** `/home/ubuntu/mde/app` 没有 `packages/`，
   没有 worker 进程，没有 crontab，`migrations/` 只有 `001` 而库里的表已经到 003。
   **本文 §0 那句「服务端的归档 worker 现在就在持续跑它们」不成立**——归档链路
   在生产上根本没有跑起来过。这不影响本次结论（四条机制都在客户端引擎里），
   但它本身是个要记下来的事实。
   → **不是缺陷，是投产门槛，且比「没启动 worker」更深一层**：`packages/` 不在服务器上，
   worker 连 import 都做不到；004–009 六份迁移的源文件同样不在。`runMigrations` 每次启动
   重跑，所以迁移只要把目录传上去 + 重启网关就会自动补齐。worker 与 scheduler 是两个独立
   进程（`bun run worker` / `bun run scheduler`），需要 `MDE_ARCHIVE_ROOT`（必填，启动时校验可用）
   与 `MDE_NAS_ROOT`。**这是 M3.5 收尾之后的下一件事。**

上一轮 Stage 8/9 停在半路，判据太靠人是原因之一——「第二遍没有产生下载流量」
写的是「看耗时，或用 `--out` 目录的文件 mtime 判断」。这种判据的问题不是不准，
是**跑完不会有人记**。本轮把其中能机器判的那部分做成了工具：

```bash
bun scripts/verify-m35.ts range    --meeting <会议号> [--type video]   # §4.1
bun scripts/verify-m35.ts snapshot --out <目录>                        # §4.2 第一遍之后

bun scripts/verify-m35.ts queue    --out <目录>                        # §4.4 / §4.5
```

它复用 `mde` CLI 的 `loadConfig` 与网关客户端，**不另写一份认证**——另写的那份
迟早与真的那份不一致，而不一致的方向是「工具说通过，真实链路不通」。
环境变量与 `mde` 完全一致。输出直接可以贴回本文的判据框。

**另一处改动**：租约时长从硬编码 900 秒改成可配（`MDE_LEASE_SEC`，默认仍是 900）。
崩溃恢复（§4.4）只能靠等租约过期来验，硬编码意味着每验一次干等 15 分钟——
这正是它至今零真实证据的原因之一。**核验时设成 10 秒，平时不要设**：
调小它在生产上是危险的（下载比租约久 → 别的实例抢走还在下的任务 →
两个进程写同一个 `.part`）。

## 2. 顺路先做一件事：查清生产库里到底有几条规则

**这条不属于 M3.5，但它决定阶段 3 的 R1 迁移方案，一起在这个窗口做掉最省事。**

背景：`policy_rules` 的排序方向要从升序改降序，判定会翻转。但代码侧侦查显示
**根本没有写规则的入口**（`PolicyStore` 只有 `listEnabledRules` 一个只读方法，
没有管理端点，`migrations/003` 也从没碰过这张表），唯一的写入来自
`scripts/seed-dev.ts` 的一条全放行规则。**如果生产库里也只有那一条，迁移方案就可以是
「显式声明现有规则集可重建」，省掉整个重排 + 逐条比对的工程。**

在 VPS 上跑：

```bash
mysql "$DATABASE_URL" -e "
  SELECT COUNT(*) AS total,
         SUM(enabled) AS enabled_count,
         COUNT(DISTINCT priority) AS distinct_priorities
  FROM policy_rules;
  SELECT id, priority, subject_type, subject_value, effect, enabled,
         JSON_EXTRACT(resource_expr, '\$') AS expr, asset_types
  FROM policy_rules ORDER BY priority ASC, id ASC;
"
```

把两段输出原样贴回来。判读：

| 结果 | 阶段 3 的 R1 迁移方案 |
| --- | --- |
| 0 条，或只有 1 条 `priority=100` 的全放行 | **声明规则集可重建**。迁移脚本清表 + 按新语义重播种，不需要逐条比对 |
| 多条但 priority 互不相同 | 排序方向翻转会**完全颠倒**判定顺序。必须重排 + 逐条比对 |
| 多条且有 priority 相同的 | 最麻烦：平局语义也在变（旧「deny 优先」→ 新「id 升序」）。必须逐条比对，且要人工确认每一条翻转 |

## 4. Stage 9 · 边界场景(**本次的核心**)

### 4.1 Range 支持 —— 先做这条,它是 4.3 的前提


- [ ] 返回 `403` → 链接已过期,重新签发。顺便记下实际 TTL：________ 秒

### 4.2 幂等（重复跑不重下）

```bash
bun scripts/verify-m35.ts snapshot --out ./m3-联调产物
```

### 4.3 断点续传（真实大文件）

挑一个**尽量大的视频**,单独跑,中途 `Ctrl-C`：


- [ ] 4.1 若是 200(不支持 Range),这一条预期会从 0 重下——**那就如实记「续传失效」**

### 4.4 崩溃恢复（租约过期重领）

```bash
# 用短租约跑这一条，10 秒就能验完，不必干等 15 分钟
export MDE_LEASE_SEC=10

cd client && bun bin/mde.ts run --meeting <会议号> --out ./m3-崩溃测试
# 看到下载开始就 Ctrl-C，制造一个停在 running 的任务

cd .. && bun scripts/verify-m35.ts queue --out ./m3-崩溃测试
# 应当看到：running N 个，其中租约已过期 N 个

cd client && bun bin/mde.ts execute --out ./m3-崩溃测试
cd .. && bun scripts/verify-m35.ts queue --out ./m3-崩溃测试
# 那些 running 应当已经被重新领取并完成

unset MDE_LEASE_SEC   # 验完就摘掉，这个值调小在生产上是危险的
```

- [ ] 卡在 `running` 的任务被**重新领取并完成**,不是永久卡住
- [ ] 服务端侧同理(MySQL 的 `SELECT … FOR UPDATE SKIP LOCKED`)：
      如果方便,在 VPS 上起两个 worker 实例跑同一批任务,确认没有重复领取
